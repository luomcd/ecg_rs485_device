## 1. 一帧画面的完整路径（从上到下）

```
① LVGL 定时器 on_frame()  每 50 ms 触发一次（ui_waveform.c）
      ↓  在 LVGL 任务上下文、持锁
② 我自己的绘制代码，直接往 canvas 的 RGB565 缓冲写像素
   canvas_fill(底色) → draw_grid → draw_baseline → draw_ruler
   → draw_wave_buf(波形) → draw_rp_marks(R 峰圆点)
      ↓  这一段的耗时 = 日志里的 `render=25.5 ms`
③ lv_obj_invalidate(canvas)   —— 只是"登记一个待刷新区域"，不画任何东西
      ↓
④ LVGL 刷新器（下次 lv_timer_handler 时）
   把待刷新区域 → 逐对象重绘 → 得到最终像素
   ★ canvas 与普通对象的差别就在这一步（见 §2）
      ↓
⑤ flush_cb（esp_lv_adapter 提供）
   把区域拷到 framebuffer（三缓冲，见 §5）
      ↓
⑥ LCD_CAM 外设按 pclk **持续**把 framebuffer 扫到屏上（不需要 CPU）
```

**关键观察**：`render` 只包含 ②。③④⑤ 的开销**不在** `render` 里，
但它们真实占时间 —— 所以"render 只有 25 ms，为什么一帧要 74 ms"的差距就在这里。

实测分解（gain5 / 25 mm/s / 有波形）：

| 段 | 耗时 | 说明 |
|---|---|---|
| ② render（我的绘制） | **25.5 ms** | fill 约 15 + 网格 6 + 波形 2~3 + 标记 <1 |
| ③④⑤ 刷新 + flush | 约 48 ms | 含 vsync 等待与 canvas→fb 拷贝 |
| 合计帧周期 | **74 ms** ⇒ 13.6 FPS | |

## 2. 关键概念：`invalidate` 的语义 —— 一切的根源

`lv_obj_invalidate(obj)` 的含义**不是"立刻重画这个对象"**，而是：
> "把这块屏幕区域标记为脏，下次刷新时，**凡是与该区域相交的对象都要重画**。"

由此推出本工程最重要的一条判据：

> ### 🎯 判据：一个显示元素"每帧要不要付代价"，只取决于它**是否与每帧被 invalidate 的区域相交**，与它是什么控件、写在哪个模块**无关**。

这条判据解释了两件事：

| 元素 | 位置 | 与每帧 invalidate 区域的关系 | 代价 |
|---|---|---|---|
| 画布角标 `5.0 s / 500.0 Hz` | 画布**外**（y=1，画布从 y=8 起） | **不相交** | **0** —— 只在文字变化时重画 |
| BPM 浮层 | 画布**内**（落在 plot 区内） | **相交** | 画布每帧 invalidate ⇒ 浮层每帧重画 |

⚠ **这就是 S4 报告 §3.2 那条"角标改 label 可省 5 ms"的真实前提**：角标在画布外。
如果把 label 放在画布内，它一样每帧重画，"用 label 更省"这个结论**不成立**。
（S4 当时没写这个前提，2026-10-26 补记。）

## 3. 为什么 canvas 只画 plot 区（752×200），不是整个 800×216

**因为 flush 的成本 ≈ canvas 的像素数**：LVGL 要把 canvas 的内容拷进 framebuffer。

```
800 × 216 × 2 B = 345,600 B
752 × 200 × 2 B = 300,800 B      ← 省 13%
```

省下的 44,800 B 每帧都要拷一次，14 FPS 下就是 627 KB/s 的 PSRAM 流量。
**这不是"少画点像素"的收益，是"少拷点内存"的收益** —— 两回事，后者才是瓶颈。

同理，四周留白（左右 24 px、上下 8 px）交给屏幕底色去填充，不占 canvas。

## 4. BPM 浮层：四个决策，每个都有代价

浮层是本工程唯一"落在画布内的独立对象"，它的每个参数都是权衡结果。

### 4.1 尺寸 160×50 —— 需求定的，也是最贵的部分

它每帧要多重绘 8000 px（含 α 混合的话），并且**遮挡**那块区域的波形。
尺寸每减一半，代价与遮挡都减半。见 §4.4。

### 4.2 位置：右上 → 右下（2026-10-26）

| 位置 | 遮挡谁 | 遮挡的是什么信号 |
|---|---|---|
| 右上（需求 §3.1 原定） | 通道 I | **R 波所在的上半区**（最关键的波形） |
| **右下（现方案）** | 通道 II | **基线以下 54~103 px**（gain5 时相当于 −2.7~−5.0 mV） |

**为什么右下更好**：心电图的主要诊断信息（R 波幅度、ST 段）都在基线上方；
基线下方 54 px 以外，正常搏动几乎不去（只有深 S 波会），所以遮挡影响最小。
⚠ 但**增益越大遮挡越严重**：gain20 时 1 mV = 80 px，基线下方 54 px 只有 0.68 mV，
S 波就会被切掉。这是"用位置换影响"的固有代价。

**几何约束（已用编译期断言固化）**：`app_config.h` 里

```c
_Static_assert(APP_BPM_Y + APP_BPM_H <= APP_BTN_BAR_Y, "BPM 浮层不得压到按钮栏");
_Static_assert(APP_BPM_Y >= APP_CANVAS2_Y, "BPM 浮层不得越出画布 2 顶端");
```

改常量越界会**编译报错**，不会画出界才发现。

### 4.3 底板为什么从 α 0.9 改成**不透明**

需求 §3.2 写 `rgba(255,255,255,0.9)`。实测：

| 底板 | 空载帧率 |
|---|---|
| α=0.9 / 0.94 | 13.7 |
| **不透明** | **14.1** |

α 混合 160×50 = 8000 px ⇒ **2.3 ms/帧**（软件逐像素混合，无硬件加速）。
而浮层底色（`#FFFFFF` / `#0F1318`）与画布底色（`#F5F5F5` / `#0F1216`）
**本来就几乎同色**，不透明后唯一可见差别是"波形穿越浮层区域时的 10% 透出"消失。
⇒ 拿 2.3 ms 换一个看不见的差别，不值。

### 4.4 "扣掉被遮挡的矩形" —— 一个理论上成立、实测失败的优化

这是本工程**最有教育意义**的一次失败，完整记录在 S7 报告 §6.14 / §6.14.1。

**想法的来源**：由 §2 的判据，浮层与画布相交 ⇒ 每帧重画。但浮层是**不透明**的，
它盖住的像素刷上去也看不见 —— 那是不是可以不刷？

**做法**：把原本的 `lv_obj_invalidate(canvas)` 换成 3 次 `_lv_inv_area()`，
提交「浮层左侧 / 下方 / 右侧」三块矩形，跳过交集（约 7,300 px = 画布的 4.9%）。

**结果**：

| 开关 | 帧率 | 画面 |
|---|---|---|
| 扣矩形（=1） | **14.1**（+0.5） | ❌ **通道 II 在浮层 x 范围内的波形整段消失** |
| 整块刷（=0） | 13.6 | ✅ 完整 |

**根因（未深究，方向明确）**：
"被遮挡 ⇒ 不用刷"这个推论**只在完全掌握刷新管线时才成立**。
显示层是第三方 `esp_lv_adapter`，它对"**不覆盖整个 canvas 对象的零碎区域**"
处理不完整（推测其 RGB flush 路径某处仍按整对象/固定跨度处理），
于是被扣掉的部分连带丢失。

**怎么发现的**（方法论比结论更值钱）：
猛哥先报"遮挡通道 II 波形"，我按几何算了遮挡区域，给出"缩小浮层"的方案；
他追问了一句 —— **"浮层顶边比基线还低 54 px，为什么那一段波形都显示不出来？"**
按几何，浮层**不可能**盖住基线附近。这一问直接推翻"遮挡"假设，指向"没被刷新"。
然后用一个编译开关做 A/B，10 分钟定案。

> **可推广的判据**：
> ① "看起来该省的地方"必须先证明**省了不出问题**；
> ② 优化的 A/B 判据要由**人眼在真实场景**确认，不能只看 fps 数字变好；
> ③ 排查"画面不对"时，先算**几何**（这块区域在物理上是否可能被盖住），
>    几何排除了就只剩刷新逻辑。

### 4.5 小结：浮层的代价账

| 决策 | 收益 | 代价 |
|---|---|---|
| 放画布内（必须，因为无空白可用） | 不占波形面积 | 每帧重画 8000 px + 遮挡 146×46 |
| 底板不透明 | −2.3 ms/帧 | 波形不透出（几乎看不出） |
| 位置右下 | 只遮基线下方的次要区域 | gain20 时会切 S 波 |
| ~~扣矩形~~ | ~~+0.5 FPS~~ | ~~整段波形丢失~~ **已废弃** |

## 5. 帧率账：瓶颈在 PSRAM，不在 CPU

### 5.1 三块缓冲的显存账

`esp_lv_adapter` 的抗撕裂模式**硬编码**为 `TEAR_AVOID_MODE_TRIPLE_PARTIAL`
（`esp_lv_adapter_display.h:74`，不是配置项），所以 framebuffer 是 **3 块**：

```
3 × 800 × 480 × 2 B = 2,304,000 B ≈ 2.2 MB PSRAM
```

📌 **不要按双缓冲的 1.5 MB 去算余量**，会差 768 KB。

### 5.2 带宽账（这就是 14 FPS 的天花板）

| 消费者 | 流量 |
|---|---|
| 面板扫描（LCD_CAM 从 PSRAM 读 fb） | 768,000 B × 33.3 Hz ≈ **25.6 MB/s** |
| 我的 canvas_fill（每帧写 300 KB） | ≈ 4.1 MB/s @13.6 FPS |
| canvas → framebuffer 拷贝（每帧读+写 300 KB） | ≈ 8.2 MB/s |
| **合计** | **≈ 38 MB/s 双向**，OCT PSRAM @80 MHz 已接近饱和 |

⇒ **提高 pclk 反而更慢**（实测 16 MHz→24 MHz，14.0→**11.6** FPS）：
面板扫描的 PSRAM 占用从 25.6 MB/s 涨到 38 MB/s，把 CPU 挤掉了。
**pclk 保持 16 MHz。**

### 5.3 为什么"波形只占 2~3 ms"却仍要小心

波形绘制的开销**不是常数**，它 ∝ 每列竖线的总长度 = 波形高度：

| 增益 | render | fps | 每帧横向跳（25 mm/s） |
|---|---|---|---|
| gain 5 | 25.5 ms | **13.6** | 10.6 px |
| gain 20 | **52.2 ms** | **9.7** | 15.5 px |

**机理**：`draw_wave_buf()` 按像素列取 min/max 后**画竖线**（这是 S4 的核心优化，
把 2500 次散点写压成 752 次竖线写）。竖线长度 = 该列样本的幅度跨度 = ∝ 增益。
gain20 时跨度是 gain5 的 4 倍 ⇒ 写入像素约 15 倍（因为 gain5 时每列只有 1~2 px）。

⚠ **所以"帧率"这个数字不带增益就没有意义**。历史记录里那个"14.5 FPS"正是因为
没写增益（而且是无九按钮栏的代码状态），导致后面反复对不上。

## 7. 加一个显示元素该怎么选（速查）

```
新元素要与波形一起每帧变吗？
├─ 是 → 直接画进 canvas 缓冲（write pixel），不要建 lv 对象
│        （对象每帧重绘 = 额外的对象遍历 + 合成）
└─ 否 → 它落在画布的 invalidate 区域内吗？
        ├─ 在 → 它每帧都会重画，代价 = 它的面积 × 每帧
        │        能挪到画布外就挪（角标区 y<8、左右 24 px 边距）
        └─ 不在 → 只有它自己变化时才重画，代价≈0
```

**本工程的实例对照**

| 元素 | 实现方式 | 理由 |
|---|---|---|
| 网格 / 基线 / 定标标尺 / 波形 / R 峰圆点 | **画进 canvas** | 每帧都变 |
| 画布角标（`Lead I`、`5.0 s / 500.0 Hz`） | 独立 label，**放画布外** | 不常变，且在 invalidate 区域外 ⇒ 代价 0 |
| BPM 浮层 | 独立对象，**在画布内** | 需要在画布之上（要盖住波形），只能付代价 |

## 9. 实测数据汇总（便于对照）

| 场景 | render | fps | dt 极值 |
|---|---|---|---|
| 空载（无波形） | 23.5 ms | 14.1 | [63, 73] ms |
| gain5 + 波形 | 25.5 ms | **13.6** | [65, 76] ms |
| gain20 + 波形 | 52.2 ms | **9.7** | [101, 103] ms |
| 双通道 gain20 | 52.8 ms | 9.8 | — |

**读法**：`dt` 极差小（±5 ms）说明帧节奏是**规整**的，顿挫感来自**帧率低**
（每帧横向跳 10~15 px），不是来自"忽快忽慢"。想改善只能提帧率。
