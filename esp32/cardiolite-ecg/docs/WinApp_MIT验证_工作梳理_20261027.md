### 3.1 W1-2 为什么要单独验

`rpeak_ref/Program.cs` 拿全量峰靠**每帧轮询** `GetDiagnostics().LastPeakIndex`：

```csharp
if (lp.HasValue && lp.Value != lastSeenPeak) { allPeaks.Add(lp.Value); lastSeenPeak = lp.Value; }
```

源码注释自己写着：「启动瞬态若一帧内连认两拍可能少记一个，评估时会计成 FN —— 如实暴露」。

**理论分析：漏不了。** 不应期 80 样本（160 ms），喂帧 25 样本（50 ms）⇒ 两次 accept 至少隔 3 帧。
**但这是推理不是实测**，而且 C# 没有单调计数器可对账（固件有 `peak_total`）。

**做法**：加 `--per-frame N`，同一条记录跑 `N=25` 与 `N=1`，峰序列**必须完全一致**。
`N=1` 时每样本轮询一次，等价于逐次 accept 记账 ⇒ 若 `N=25` 与它一致，轮询无漏。

> 📌 这一步纯在 CardioLite 侧做（`tools/rpeak_ref/Program.cs`），**不动 WinApp**。

### 4.1 W2-2 两个必须当场确认的设置

> **raw853 不是前置条件**（2026-10-28 订正，猛哥指正）：`.bin` 走 `ascii-0` 二进制档，
> `_braw853` 上电默认 **0 = 500 Hz 重采样输出**（`ads1293.c:39-44`），录 `.bin` **天然就是 500 Hz**，无需任何动作。
> 853 Hz 是 `test ascii-1` + `test raw853 on` 组合才产生的**文本调试流**（抓 txt 用），与 W2 要录的 `.bin` 是两条独立路径。

1. **notch 状态记录清楚**（STA bit1）。AFE 报告已证明 notch 对精度影响 ≈0，但**对账时两边必须同状态**。
2. **标准播放顺序**：`start → 记录(开始) → AECG100 播放 … → 播放结束 → 记录(停止)`，**先点记录后点播放**，
   保证**首尾都是基线**（波形段夹中间）。检测器**从首部基线开始喂**让它自举，**只对波形段逐峰比**。
   （2026-10-28 订正：不再"掐前 6.15s"——那是 W1 数字基线无空白时的旧口径，见 §4.3 / 指南 §8.1b）

### 4.2 录像件怎么回到 ESP32（零代码）

WinApp 录制的 `.bin` 是**标准 T101 v2.2、LEN=53、25 样本/帧、STA=0x02 ⇒ 500 Hz**（10-26 八条阶梯录制已逐条核实，帧数×25 与墙钟时长吻合）。
> STA 字节 bit 含义（`ads1293.c:1146-1151`）：bit0 mode / bit1 notch / bit2 channel / **bit3 raw853** / bit4 LOD。
> 故 `STA=0x02` = notch on、**raw853 off**（bit3=0）⇒ 500 Hz 降采样流，`0x02` 本身是 notch 位、非 raw853。
⇒ 直接拷到 SD 卡根目录、改名 `ecg.bin`，CardioLite 能播。

⚠ 副作用：`main.c:208` 的 S2 自检表按文件写死了期望帧数，换文件后会报 FAIL。**只影响自检日志，不影响回放**；在意就把那行期望值改成实测。

### 4.3 ✅ W2-4 对账结果（2026-10-28，首条真实录件）

**标准播放顺序（2026-10-28 定，以后所有 W2 录制一律照此）**：

```
start → 记录(开始) → AECG100 播放 … → AECG100 播放结束 → 记录(停止)
```

先点记录、后点播放 ⇒ 录件的**首尾都是基线**（无波形），波形段夹在中间。这条顺序是
W2 对账的**前提**，不是可选项：它让检测器在首部基线里完成阈值自举，进入波形段时已收敛，
同时尾部基线留出 AFE 直流恢复时间。

**做法**：录件 `ecg_20261028_104807_W2-2-001.bin`（播 `100_60s.txt`，诊断档+陷波开）→
互相关定界出波形段 → **检测器从首部基线开始喂**（让它自举完再进波形）→ 只对波形段逐峰比。

**几何（互相关定界，相关系数 0.989）**：
- 录件波形段 = 样本 `[3025, 33025)` = 30000 样本 = 精确 60 s @500Hz，恰落在帧 121~1320（1200 帧）整边界。
- 三段结构：`[前空白 6.05s 基线] [波形 60s] [尾部衰减 6.65s]`，首尾基线由标准播放顺序保证。
- 真值 = `100_ann500.txt` 前 60 s（`sample500 ≤ 30000`）的 **74 个搏动**。

**对账结果**（匹配窗 ±75 样本；🛑 口径见下，**不是**「排除首尾 5s」）：

| 喂法 / 口径 | 真值 | TP | FP | FN | Se | +P | DER |
|---|---|---|---|---|---|---|---|
| 只截波形段硬喂（旧，硬切一刀） | 74 | 74 | 2 | 0 | 100.00 | 97.37 | 2.70 |
| **含首部基线完整喂 + 全波形段** | 74 | 74 | 1 | 0 | 100.00 | 98.67 | 1.35 |
| **含首部基线完整喂 + 排除波形起点 0.1s** | 74 | 74 | **0** | 0 | **100.00** | **100.00** | **0.00** |

**🛑 口径订正（本条录件首尾基线，旧「排除首尾 5s」口径作废）：**

- 「排除首尾 5s」是为 **W1 数字基线**（从样本 0 直启、无空白，自举期撞上首个搏动）设计的口径。
  用在这条**首尾基线**的录件上是**错的**：它会误伤波形段最前面 12 个真搏动（真值首搏在 0.214s）。
- 正确口径 = **按波形段边界对账 + 只排除波形起点 0.1s 的人工切割沿**。
- 那条唯一被排除的 FP（@局部样本 8 = 0.016s）是「基线→波形」的**陡变沿**（局部 0~20 样本均值
  −8→−915 的跳变），是人工切割造成的边界假峰，**与模拟链路、算法能力都无关**。

**三个结论：**

1. **硬件闭环一个峰都没吃掉**：正确口径下 W2 波形段 **Se 100% / +P 100% / DER 0%**，74 拍零漏零误。
   ⇒ 模拟链路（D/A + 接线 + AFE + 853→500 重采样）在这 60 s 上的代价 **Se 差 = 0**，
   远小于判据 ≤0.1 pp。**W2 判据首次落账，通过。**

2. **首部基线的自举确实发生了**：首部空白段（全局 0~3025，std=25 纯基线）里检测器报了 **28 个假峰**，
   全是把基线噪声当峰——这正是 6.15s 阈值自举期的体现。但**这些假峰都在波形段之外**，
   不影响波形段对账。

3. **首部基线有价值**：含首部基线完整喂时，波形段内 FP 从 2 个降到 1 个（原来的 FP@862 消失了）——
   因为检测器在空白段把阈值建立起来，进入波形段时不再把同一个 QRS 双检成两个峰。
   ⇒ 标准播放顺序的「先记录后播放」不只是方便，它直接改善了对账质量。

`w2_2_001_det.txt`（76 峰）、`w2_2_001_truth.txt`（74 真值）。

### 7.2 📌 W1-4 分账：窗宽 vs 精度各自吃掉多少（2026-10-28 实测，108,887 拍）

三引擎 W=40 全部就位后，两个变量的影响可以精确拆开：

| 变量 | 引擎对 | TP | FP | FN | Se | DER |
|---|---|---|---|---|---|---|
| **窗宽 55→40** | host float（同引擎） | +30 | −33 | −30 | +0.03 pp | −0.06 pp |
| **精度 float/double** | 同窗 W=40，float − double | **−42** | −1 | **+42** | −0.04 pp | +0.04 pp |

**两个结论：**

1. **窗宽 55→40 是净赚的**：TP +30、FP −33（假峰少 33、真峰多 30），且全部集中在难例。这是 Q6 定案「更准:更差 5.7:1」的又一次旁证。

2. **float 比 double 单向多检 42 拍**（15 条差异记录里零条反向，全在 FN 高的难例、FP 几乎不动）。
   这与 W=55 时代的「float 单向多检」结论**方向一致**，只是现在有了 W=40 的精确数字。
   ⚠ 这条**别写成「float≡double」**：30 条干净记录逐位一致，但 15 条难例 float 系统性多检、零条少检 —— 是**单向偏置**，不是随机抖动。
   根因是 float 累积误差在低幅/噪声段把阈值算得略松（记忆里「float/double 在噪声段可能分叉」）。

**对 W2 判据的含义**：模拟链路那 ≤0.04 pp 的真实影响，现在和一个**同量级的 float/double 偏置（0.04 pp）**叠在一起。
W2 对账时，板载(float) vs C#(double) 的 0.04 pp 差异**不能全记给模拟链路**，里面混着精度偏置。
好在 W2 判据（Se 差 ≤0.1 pp）本身留了 2.5 倍余量，0.04 pp 精度偏置不构成威胁，但**对账口径要写清楚"板载 vs C# 差了 float/double 这一层"**。

### 7.3 📌 W1-5 三栏对照：float 单向多检的精确分层（2026-10-28）

工具 `tools/cmp_three_engines.py`（三份 csv 直接对照，无需重跑），产出：

| 分层（DER 1.4% 界，34/14） | C# double W=40 | host float W=40 | ΔTP(float−C#) |
|---|---|---|---|
| 干净组（34 条） | Se 99.70 / DER 0.39 | Se 99.72 / DER 0.37 | **+16** |
| 问题组（14 条） | Se 97.59 / DER 5.24 | Se 97.67 / DER 5.17 | **+26** |
| 全量 | 99.07 / 1.84 | 99.11 / 1.80 | **+42** |

**逐条分布**：33 条逐位一致 + 14 条 float 多检（合计 +42，**零条反向**）+ 1 条换位（107 号，仅 float 多 1 个 FP，TP/FN 不动）。

**两个被这条数据修正的旧印象：**

1. ~~「float/double 差异只在噪声段」~~ —— **不成立**。干净组（DER 0.39%）里 float 依然多检 16 拍，
   占 42 拍的 38%。差异是**全局性的精度偏置**，不是"难例才触发"，只是问题组里幅度更大（26 vs 16）。

2. **「float 单向多检」在新窗下依然成立、且更干净**：W=40 下 14 条 float 多检、零条反向；
   换位从 W=55 时代的 3 条降到 1 条。窗收窄（55→40）本身就把 float/double 的歧义收敛了一部分。

**对 W2 对账的最终口径**：板载(float) 对 C#(double) 天然差 +0.04 pp（float 多检），
这个偏置**从干净组到问题组都在**。W2 判据 Se 差 ≤0.1 pp 时，要把它单列为"已知精度偏置"，
否则会把 0.04 pp 的浮点差异误判成模拟链路的 ±0.04 pp 扰动，方向都分不清。
