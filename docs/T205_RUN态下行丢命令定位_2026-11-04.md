# T205 · RUN 态下行丢命令定位（2026-11-04）

> **⚠ 2026-11-04 下午定案（本文 §7）：T205 的「下行丢命令」不存在，是测量伪影。**
> 真凶＝**ST-LINK 的 SWD attach**。只要测试脚本在下发窗口附近读一次内核变量，
> UART5 的 RX 就会被 halt 打断并报溢出错误（零串口输入下 10 次 attach ⇒
> `comm_rx_loss` **+41**），当前那包 8 字节只剩半截。
> 不碰 SWD 时实测 **100/100、20/20、80/80、10/10 全中**，一次没丢。
>
> 下文 §1~§8 是**当天的错误结论与推导过程**，保留作反面教材；
> **请以 §7 为准**。

## 1 起点与两次自我推翻

上轮（T204）结论是「RUN 态下行 **0%**，STOP 态 100%」。本轮先推翻了自己两次：

| # | 我先前的说法 | 怎么被推翻 |
|---|---|---|
| ① | RUN 态下行 0/10、0/5 ⇒ **完全不通** | 小样本假象。实测 p≈0.17~0.33；p=0.2 时 0/10 仍有 0.8¹⁰≈**11%** 概率发生 |
| ② | 「`comm_rx_events` 在涨 ⇒ 字节到了 STM32」 | **缺空白对照**。静默不发命令时它自己就涨 ⇒ 该判据不成立（后来查明正是 SWD attach 造成的） |

🛑 两条通用纪律（本轮挣来的）：
- **报「0/N」前先算「若 p=X，0/N 的概率是多少」**；
- **用增量型计数器做判据，必须先做空白对照**。

## 3 两次判据事故（方法论，永久有效）

### 3.1 滞后积压帧 —— `_t205n`

每轮只读 12 帧，两次取样之间夹着 1~3 s 的 SWD 调用；设备照常 ≈19 fps 产帧
⇒ CH340 内核缓冲积压只增不减，**我永远在读几秒前的旧帧**。表现就是「STA 直方图
恒定 `0x02×12` 一动不动」。

✅ 正确写法：**取样前 `reset_input_buffer()` 丢掉积压，只读新到的帧**。改完 STA 与
芯片 `f64.notch_on` **6/6 逐条一致**。

### 3.2 幂等命令被算成「成功」—— `_t205l`

`want = 1 - STA`，STA 卡在 0 ⇒ 每轮都发 `notch=1`；而
`ecg_filter_f64_set_notch` 是**幂等**的（`ecg_filter.c:808`）⇒ 第 3~6 次下发是
**空操作、根本不可能失败**，却被算进「芯片 5/6」。

✅ 正确写法：**目标值由芯片状态反推**（`want = 1 - f64.notch_on`）。

## 4 字节级证据：芯片收到的是「帧尾巴」

`_t205q` 每轮先 SWD 清零三块缓冲，再发 `AA 55 80 02 00 05 00 FA`，再 dump：

```
#3  work = 00 55 80 02 00 05 00 FA   pub0 = AA 55 80 02 00 05 00 FA   ⇒ 生效 ✓
#1  pub1 =          02 00 05 00 FA                                   ⇒ 未生效
#4  pub0 =          02 00 05 01 FD   pub1 = 80（单独一包）            ⇒ 未生效
#5  pub0 = 80（只剩 1 字节）                                          ⇒ 未生效
```

**完美 1:1 相关**：`clean_frame` ⇒ 生效 4/4；`garbage/fragmented/no_event` ⇒ 生效 **0/10**。

⇒ 解析器、CRC、长度对核、状态门、内核 setter **全部无罪**；
损害发生在 **UART5 收字节这一层**，且「帧头 2~3 字节被吞」。

## 7 定案：真凶是 SWD attach（2026-11-04 下午）

### 7.1 单变量实验

| 模式 | 脚本 | 结果 | `rx_loss` |
|---|---|---|---|
| **全程不碰 SWD** | `_t205p` / `_t205t` | **100/100、20/20、80/80、10/10** | **恒定不动**（13 冻结 175 s） |
| 每条命令前后各一次 SWD 读 | `_t205t --swd` | 8/10 | 0 → **23**（Δ23 / 20 次 attach） |
| 每轮 3~5 次 SWD 读写 | `_t205m/o/q` | 0~40% | 每条命令 **+2.8** |

### 7.1b 猛哥指令的正面复核：三轮「复位前 vs 复位后」

全程不碰 SWD（纯净法），每轮各 10 次：

| 轮 | 复位**前** | 复位**后** |
|---|---|---|
| 1 | **3/10 = 30%** ← 上一轮结尾刚做过 10 次 SWD attach（`rx_loss` +41） | 脚本只等 2.5 s，无上行帧（**工具时序问题**，非板子故障） |
| 2 | 10/10 = 100% | 10/10 = 100% |
| 3 | 10/10 = 100% | 10/10 = 100% |
| 补测 | —— | 10/10 = 100%（等 4 s） |

**合计：复位后 30/30 = 100%；复位前 23/30，唯一失手那次正好紧跟在 SWD attach 之后。**

⇒ 两种说法都对，但因果要摆正：
- **猛哥的经验成立**——复位一次，立刻回到 100%（这是工程上最省事的保底手段）；
- 但**复位不是必需品**：只要不给 SWD 干扰，复位前同样是 100%（第 2、3 轮各 10/10）；
- 复位真正清掉的，是**被 SWD attach 打出来的 UART 错误态**，不是固件的什么毛病。

⚠ 工具注意：硬复位后 `_t205p` 要**等 ≥4 s** 再跑，否则会误报「无上行帧」。

### 7.2 决定性一刀：零串口输入

```
只做 SWD 读、一个串口字节都不发：
  起点 rx_loss = 38
  10 次 SWD attach 之后 rx_loss = 79      ⇒ Δ = +41（每次 attach 4.1 个错误）
```

**没有任何串口输入**，UART 却报了 41 个错误 ⇒ `STM32_Programmer_CLI` 每次
`-c port=SWD mode=hotplug` 都要 attach 调试器，attach 期间**内核被短暂 halt、
中断不响应**；UART 硬件照收字节但没人搬 ⇒ **ORE 溢出** ⇒ HAL 走
`UART_EndRxTransfer()` 终止接收 ⇒ 当前那包只剩半截，随后
`HAL_UART_ErrorCallback`（`comm_port.c:249`）再把接收重挂上。

这正好解释了 §4 看到的「**帧头 2~3 字节没了、尾巴孤零零留下**」——
不是总线上丢的，是**我自己的调试器把 CPU 按住的那几百微秒里丢的**。

### 7.3 与猛哥观测完全对齐

| 现象 | 解释 |
|---|---|
| WinApp 点 START/STOP/陷波，**次次生效** | 没有调试器在旁边按暂停 |
| `_t205i` 旁证 10/10 | 那一轮我只在点击**之后**采样，正好避开了下发窗口 |
| 我测得 0~40% | 每次下发前后都插了 SWD 读/写 |
| 「STA 判据 0/6」 | 额外叠加了 §3.1 的滞后积压帧 bug |

### 7.4 固件结论

**UART5 命令通道无缺陷，T205 原计划的 §6.3 三条加固（`Size<4` 丢弃 / 缓冲内
搜 `AA 55` / 带计数待处理队列）撤销，不改源码。**

唯一值得保留的是 `comm_port.c:249` 那个 `HAL_UART_ErrorCallback` 重挂 ——
T201 已落盘，它正是「一次噪声不永久失聪」的保命件，本次实验反过来证明了它的价值：
SWD attach 制造了上百次 ORE，接收每次都自动活了回来。

### 7.5 今后测下行成功率的铁律

1. **测成功率时，下发窗口里绝对不碰 SWD**；要看芯片状态就拿串口 STA
   （**取样前必须 `reset_input_buffer()`**，见 §3.1）。
2. 必须用 SWD 时，**把它挪到两次下发之间的长间隔里，并在报告里注明**——
   否则测的是调试器，不是固件。
3. **目标值由被测状态反推**，别用受污染的量（§3.2）。
4. 建议保留「上位机连发 3 次」作为工程习惯（零成本），但它**不是本次问题的解**。
