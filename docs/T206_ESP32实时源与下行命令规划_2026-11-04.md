# T206 · ESP32 侧实时源 + 下行命令规划（2026-11-04）

> **结论先行**：收方向**已经做完了**，不用重写；缺的只有两块——
> **① 下行命令帧（`rs485_send()` 空有、没有帧构造函数）**
> **② UI 接线（模式/陷波/通道三键仍灰显；`app_state` 只有回放四态）**。
> 回放版**原样保留**，用编译期宏切源（§2），两套路径共存、共用「push 之后」的全部代码。
>
> **★ 本设计的第一不变式（猛哥 11-04 拍板⑤）**：**进入 RUN 之后 ESP32 一个下行字节都不发**
> ——配置全在 STOP 态完成（此时总线上没有帧流，485 空闲）。
> 于是「半双工冲突 / 单槽交接被覆盖 / 命令静默丢」这类风险**结构上消失**，不靠实测概率兜底。

## 1 现有家底（已核实到行号）

### 1.1 硬件通路

```
ADS1293 → STM32L476(UART5: PC12/PD2) → TTL → RS232 → 232转485(UT-2211) → 485 → ESP32(UART1) → LCD
```

ESP32 侧收发器（`app_config.h:279-303`）：

| 项 | 值 | 备注 |
|---|---|---|
| 收发器 | **SP3485EN**，VCC=3V3 | RE/DE 短接，由 **Q1 硬件自动切换方向** |
| UART | **UART1**（不用 UART0） | ROM console 会往 IO43 打日志，自动方向电路会把总线拉进发送态 |
| TX / RX | **GPIO44(→DI) / GPIO43(←RO)** | 🛑 引脚是**交叉**的，与 S3 默认 U0TXD=43/U0RXD=44 相反 |
| 波特率 | 115200 8N1 | 带宽 11.52 KB/s，单通道 59 B×20 fps = **1.18 KB/s（余量 9.8×）** |
| 缓冲 | RX 4096 / TX 2048 / 事件队列 20 | 4096 ≈ 68 帧 ≈ 1.7 s |
| 终端 | 120Ω 由 **SW2 拨码**选通 | A=P1-10、B=P1-9 |

🛑 **固件不控 DE**（Q1 自动方向）⇒ **没法做「发送期间禁收」**。半双工冲突只能靠
时序规避 + 幂等重发兜底，不能靠方向控制（§3.4）。

## 3 发方向：命令层（新增 `main/ecg/ecg_cmd.c/.h`）

### 3.1 帧格式（与固件 `vcomcmd.c` 对齐，勿改）

```
AA 55 | 0x80 | LEN(2,LE) | CMD | ARG(0~N) | CRC8        总长 = 6 + LEN
LEN = 1(CMD) + 1(ARG) = 2（带参命令）
CRC8：poly=0x07 / init=0x00 / 不反射，覆盖 TYPE+LEN+CMD+ARG
例：notch=0  →  AA 55 80 02 00 05 00 FA
```

### 3.2 支持的命令与状态门（**照固件口径，别猜**）

| CMD | 语义 | 固件状态门 | ESP32 何时用 |
|---|---|---|---|
| `0x01` | START | **无门**（`vcomcmd.c:674`） | 配置完成后发一次（**唯一进入 RUN 的动作**） |
| `0x02` | STOP | **无门、幂等**（`:700`） | 🛑 **不作为用户按钮**（猛哥 11-04 拍板）；仅上电配置流程内部用 |
| `0x03` | RESET | 无门（`:662`） | 异常恢复（可选，默认不用） |
| `0x04` | SET_MODE（诊断/监护） | **无门**（`:706`） | **仅 STOP 态**（本设计自律，非固件要求） |
| `0x05` | SET_NOTCH | **无门**（`:727`） | **仅 STOP 态**（同上） |
| `0x06` | SET_CHANNEL（单/双） | 🛑 **仅 STOP**（`:755`） | 配置阶段 |
| `0x10` | REQ_SNAPSHOT | 🛑 **仅 STOP**（`:652`） | ★**既做配置核对，又做 RUN/STOP 探针**（§5.1） |
| `0x11` | SET_REGS（差异化写） | 🛑 **仅 STOP**（`:791`） | ★**START 前同步用**（见 §5.2） |
| `0x12` | SET_REGS_FORCE（实验写） | 🛑 **仅 STOP**（`:810`） | ★**START 前同步用**（放行全部 36 条） |

### 3.3 接口草案

```c
/* ecg_cmd.h */
esp_err_t ecg_cmd_send(uint8_t cmd, const uint8_t *arg, uint8_t arg_len);
esp_err_t ecg_cmd_start(void);                 /* 0x01，连发 3 次 */
esp_err_t ecg_cmd_stop(void);                  /* 0x02，连发 3 次 */
esp_err_t ecg_cmd_set_mode(bool mon);          /* 0x04 */
esp_err_t ecg_cmd_set_notch(bool on);          /* 0x05 */
esp_err_t ecg_cmd_set_channel(bool dual);      /* 0x06，内部判 STOP 态 */
esp_err_t ecg_cmd_snapshot(void);              /* 0x10，内部判 STOP 态 */
esp_err_t ecg_cmd_regs_force(const uint8_t *items, uint8_t n);  /* 0x12，(REG,VAL)×n，n≤28 */
esp_err_t ecg_cmd_sync_golden(void);           /* ★0x10 取样→比对金标→0x12 分批下发→复核 */
```

- **不缓存"我以为的状态"**：一律以**上行 STA** 为真值（`app_state.sta`）。
- 拼帧直接复用 `ecg_crc8()` 与 `ECG_STA_BIT_*`，**不新写 CRC、不新定位定义**。
- 状态门不满足时**返回 `ESP_ERR_INVALID_STATE` 并打日志**，绝不"静默发出去然后没反应"
  ——那样现场会误判成通信故障。

### 3.4 发送时机与重发

因为拍板⑤「RUN 态零下行」，**所有命令都落在 STOP 态**，此时：

- 上行帧流**根本没开始**（显示帧只在 RUN 发）⇒ 总线空闲 ⇒ **没有半双工冲突**；
- 主循环不忙 ⇒ 单槽交接**没有第二帧来抢**；
- 所以「连发」不再是抗丢的主力，只是**保险丝**：`0x01/0x02/0x03/0x04/0x05` 全幂等，
  连发 3 次 / 间隔 20 ms，零副作用。`0x06`/`0x10` 同样可以连发（幂等读/幂等写）。

🛑 唯一要防的是**反向问题**：连发会不会造成副作用？
- `0x04/0x05/0x06` 都是**幂等 setter**（`set_mode`/`set_notch` 内部有 `if (相等) return;`
  ⇒ 重复发**不会**重做 DC 预置，不会产生额外波形瞬态）；
- `0x10` 是纯读；
- `0x01` **不幂等**（重发会重走采集链初始化）⇒ `ecg_cmd_start()` 内部**只调一次发送**
  （连发 3 帧仍由同一函数完成，但要靠 `cmd_start_pending` 标志挡住用户重复点击，见 §8.2）。

## 4 UI 改造

### 4.1 新增实时态（`app_state`）

```
APP_LIVE_IDLE   已连上、STOP 态（可配置）
APP_LIVE_RUN    正在收帧（START 之后）—— 配置键全部灰显
APP_LIVE_LOST   曾收到过帧、之后超过 2 s 无帧（断链）—— 配置键同样灰显（不知道对面还在不在跑）
```
🛑 回放四态**保留不动**，用 `#if APP_DATA_SOURCE` 分派，不要合并成一套。

### 4.2 九键在实时模式下的语义（**无新增键**）

| 键 | STOP 态（可配置） | **RUN 态（START 之后）** |
|---|---|---|
| 开始 | ★**先同步寄存器再 START**（§5.2 五步），成功后进 RUN | **灰显**（已在跑） |
| 冻结 | 本地停绘制 | 本地停绘制（**不发命令**，需求 §8.3） |
| 清屏 | 本地清环缓/R峰/BPM | 同左（**不发命令**） |
| 增益 / 走纸 | 本地画布 | **本地画布（可点，零下行）** |
| 诊断 | 发 `0x04` | **灰显** |
| 陷波ON | 发 `0x05` | **灰显** |
| 通道I | 发 `0x06` | **灰显** |
| 回放 | 切回放源（或灰显） | 灰显 |
| ~~停止~~ | —— | **不设**（拍板②） |

🛑 **本设计的核心不变式：一旦进入 RUN，ESP32 一个下行字节都不发。**
配置只在 STOP 态发生，而 STOP 态**没有上行帧流** ⇒ 485 总线空闲 ⇒
既无半双工冲突、也无单槽交接被覆盖的窗口。风险是**结构上消失**，不靠实测概率。

### 4.3 回显口径（照抄 WinApp，别自创）

- 点击时只做**乐观高亮**；
- **下一帧用 STA 顶回**：bit0 mode / bit1 notch / bit2 channel（bit3 raw853、bit4 LOD 本轮不用）；
- 若 2 帧内 STA 没翻转 ⇒ 撤销高亮 + 记一条 `cmd_miss`（可显示为小圆点，便于现场排查）。
- 🛑 **禁止用"本地按钮态"当状态显示** —— 那正是「看起来成功、其实没发」的经典坑。
- 🔑 RUN 态的按钮状态**全部来自 STA**（不是来自"我刚发过什么"），所以哪怕 ESP32 中途重启
  也能立刻显示采集端的真实状态。

## 5 上电/连接序列（真机通路）

```
上电 → UART1 装好 → 观察 1.5 s：有没有上行帧？
  ├─ 有帧  ⇒ 对面已在 RUN ⇒ 进 APP_LIVE_RUN，按 STA 显示，**不发任何命令**
  └─ 无帧  ⇒ 可能 STOP，也可能没接/断线 ⇒ 发 **0x10 探针**（§5.1）
        ├─ 1 s 内收到 TYPE=0x03 快照 ⇒ 确认 STOP ⇒ 允许配置
        └─ 超时 ⇒ APP_LIVE_LOST，配置键灰显，每 2 s 重探
用户配置（STOP 态）：
   0x04 设模式 / 0x05 设陷波 / 0x06 设通道
   → 0x10 再读一次快照，**逐位核对 STA**
   → 0x01 START（连发 3 次）⇒ 进 RUN，此后零下行
运行中：连续 2 s 无帧 ⇒ APP_LIVE_LOST；恢复后**只恢复显示，不重发 START**
        （对面没停，重发 START 会二次初始化采集链，会产生基线瞬态）
```

### 5.1 ★用 `0x10` 当 RUN/STOP 探针（零副作用）

`0x10 REQ_SNAPSHOT` 在固件里**只在 STOP 态回一帧 `TYPE=0x03` 快照**，
RUN 态**静默返回**（`vcomcmd.c:652`）。所以它是天然的、
**纯读、无副作用、不需要 STOP 按钮**的状态探针：

| 探针结果 | 判读 | 动作 |
|---|---|---|
| 回 `0x03` 快照 | **确定 STOP** | 允许配置；快照内容还顺带给出全部真实配置 |
| 1 s 超时 | RUN 或断链 | 配置键灰显，**绝不盲发** `0x06`/`0x11`（发了也是白发） |

这样解决了「ESP32 中途重启、不知道 STM32 在不在跑」的死结，
而且完全不需要给用户一个 STOP 按钮。

🛑 判据注意：`0x03` 快照与 `0x01` 显示帧的 **TYPE 不同**，解析要按 TYPE 分流，
不能只认 `AA 55`（否则会把显示帧当成快照回应，永远误判成 STOP）。

### 5.2 ★START 前的寄存器同步（猛哥 11-04 追加）—— 机制已查清，必要性待实测

**现象（猛哥）**：每次上电后 ADS1293 寄存器里有异常值，**勾「实验写」点「同步」之后
START 才正常**。下面的 §5.2a 是「同步为什么必须是实验写」，§5.2b/§5.2c 是
「同步到底是不是 START 的必要条件」—— **两者是不同的问题，别混**。

#### 5.2a 「勾实验写才有效」为什么成立（代码层面完全对得上，已核实到行）

| 事实 | 位置 | 后果 |
|---|---|---|
| `ads1293_start()` 第③步**写全表 36 条 + 逐条回读** | `ads1293.c:804/810` | 任一条不一致 ⇒ `bad>0` ⇒ **不起流、停回 STOP** |
| 该路径**不回显** | `vcomcmd.c` 的 `0x01` 段 | 上位机只能靠 **1.5 s 超时**看出来 ⇒ 现象就是「START 没反应」 |
| 失败时留痕 | `_wt_fail_reg/want/got`，`0x20000980/81/82`（T170-A） | 可直接读出**是第几条、期望值、实测值** |
| `0x11` 白名单**整批预扫** | `ads1293.c:703` 前 | 差异集里**混进 1 条硬拒项 ⇒ 一条都不写** |
| 硬拒 7 条 = `0x11/0x12/0x13/0x21~0x24` | `_reg_writable()` | 参考/时钟/抽率链；普通同步会被整批拒掉 |
| `0x12` 实验写 `allow_protected=1` | `:810` | **整批放行 36 条** ⇒ 这是「勾实验写才有效」的原因 |

**数值上并不换值**：`expected_regs.json` 的 36 条与固件 `regs_leaderIII` **逐条相同**
（已逐条核对：0x01=0x11 / 0x02=0x19 / 0x06=0x08 / 0x0A=0x07 / 0x0E=0x00 / 0x17=0x05 /
0x2E=0x33 / 0x2F=0x30 / 0x11=0x00 / 0x12=0x04 / 0x13=0x00 / 0x21~0x24=0x02 / 其余 0x00）。
⇒ **实验写的作用是"绕过整批拒绝、强行重写"，不是"换成正确的值"**。

### 5.2b ★★另一条更可能的解释：**上位机自己的 H 组硬闸**（11-04 晚追查，此前漏看）

`Form1.cs:1050`（`ToggleStartStop()` 的 START 分支第一句）：

```csharp
if (lastValidation is not { CanStart: true })
{
    MessageBox.Show(this, "配置校验未放行，无法 Start。\r\n\r\n…", "禁止 Start", …);
    return;                       // 🛑 一条命令都不发，0x01 根本没出去
}
```

`CanStart` 的定义在 `ConfigValidator.cs:53`：**`HardFailures.Count == 0`**，即
**H 组 11 条全一致**。H 组（`expected_regs.json` 的 `grade:"H"`）＝

| 分组 | 寄存器 | 是否固件硬拒 7 条 |
|---|---|---|
| H1 电极映射 | `0x01` `0x02` | 否（可写） |
| H4 读回通道 | `0x2F` | 否（可写） |
| H5 DRDY 源 | `0x27` | 否（可写） |
| H2 频率链 | `0x13` `0x21` `0x22` `0x23` `0x24` | **是** |
| H3 参考/时钟 | `0x11` `0x12` | **是** |

而 **ADS1293 上电停在 POR 默认值**：固件侧**没有任何 GPIO 控 ADS1293 的 RESET 脚**
（`Core/Inc/main.h:60-67` 只有 `ADS_CLK/MISO/MOSI/CS` 四个，全库检索 `ADS_RESET`/`RST_Pin`
零命中）⇒ **只有整板断电才会让芯片回到 POR**。⇒ H 组**必然**与金标不一致 ⇒
`CanStart = false` ⇒ **WinApp 连 0x01 都不发**。

这完全解释猛哥的体验，而且**不需要假设芯片写不进去**：

```
上电 → 读快照 → H 组不一致 → 点 START 被界面拦（"禁止 Start"）
     → 勾「实验写」点「同步」→ 0x12 把 11 条 H 全写成金标
     → 重读快照 → CanStart=true → 再点 START，这次发出去了 ⇒ "才能正常START"
```

⇒ 「必须同步才能 START」**至少有相当概率是上位机的闸门，不是芯片的限制**。
这两件事必须分开测，否则 ESP32 侧会照抄一个可能根本不存在的约束（凭空多一条 12 帧的下行序列，
还多一个失败点）。

### 5.2c 判据：两种分支，对应两种设计

| 分支 | 判据（实测） | ESP32 侧该怎么办 |
|---|---|---|
| **A** 裸 `0x01` 在 POR 态就能起流 | `_t206a --no-reset` 报「2 s 内 ≥3 帧」 | 固件写全表本来就够 ⇒ **同步不是功能必需**。同步只作为「值与金标一致」的留痕/校验用；若不做，也不影响起流。建议**仍做**，代价小、且和 WinApp 行为一致 |
| **B** 裸 `0x01` 起流失败 | 无帧 + `_wt_fail_reg/want/got` 有值（`0x20000980`） | 芯片 POR 态确有写不进去的项 ⇒ **同步功能必需**，按下述五步走 |

判据脚本（已加固，一次上电拿全答案）：

```
# 整板断电重上电后**立刻**跑（不要先开 WinApp，它会先写一遍命令）
python tools/_t206a_pwr_snapshot.py --port COM27 --no-reset --sync-retry
```

它依次给出：POR 36 条 vs 金标的逐条对比表 → **裸 0x01 是否起流** →
（失败时）`_wt_fail_*` 坏项定位 → 0x12 分批强写差异集 → 复核归零 → 再 0x01。

**B 分支的 START 流程**（A 分支可整段省略）：

```
点「开始」
  ① 0x10 读快照（确认 STOP + 拿到 36 条真实值）
  ② 与内置金标表逐条比对 ⇒ 得出差异集 items
  ③ 差异集非空 ⇒ 0x12 SET_REGS_FORCE 下发（🛑 分 2 批：28 + 8，因 VCOM_BIN_MAX_LEN 限 n≤28）
  ④ 再 0x10 读一次快照，确认差异已归零（每帧 0x12 成功都会回一帧快照，共用同一回执）
  ⑤ 0x01 START
```

🛑 两条纪律：
- **一律走 `0x12`，不要试图"能写的发 0x11、硬拒的发 0x12"** —— 那会产生两帧快照，
  上位机会多出一次「未登记的 ACK」（`ads1293.c:684-690` 注释明写）。
- **差异集为空也要发一次全表**（可选）：活体上这是 no-op，但它是"芯片状态确实被写过一遍"
  的证据；成本 2 帧（28+8），在 STOP 态、无帧流，不影响任何时序。

**ESP32 需要新增的数据**：内置 `regs_golden[36]`（来源 = WinApp 的
`Config/expected_regs.json`，已核对与固件表一致）。这是本轮必须落的一份常量表。

⚠ **已实测否掉的一半**：`_t206a_pwr_snapshot.py` 在**只做 STM32 NRST** 的条件下 —
36 条里只有 `0x00=0x01` 不同（**ADS1293 不受 STM32 的 NRST 复位**，芯片仍停在 RUN），
且 **START 成功起流（2 s 43 帧）**。⇒ NRST 这条路径**证明不了也否定不了** B 分支，
必须整板断电重上电。

### 5.3 ★★T207：固件上电写默认表（猛哥方案，2026-11-04 14:54，已落码并构建通过）

猛哥一句话把问题从「ESP32 每次补一遍」挪到了「**根上补一次**」：

> 你可以在 stm32l476 这端，上电初始化 ads1293，就把默认的寄存器的值写入 ads1293。

这是**正确的一刀**，理由：坏的是「上电后寄存器不在已知态」，那就在上电时把它们置到已知态；
不让每个上位机（WinApp / ESP32 / 未来的任何主控）各自补一遍，也不引入「金标表版本耦合」。

**落点（三处，共 ~60 行，含注释）**：

| 文件 | 改动 |
|---|---|

1. 全程走 `ads1293_conversion_run(false)`（无 delay/无回显），🛑 不用 `ads1293_conversion()`；

4. 表首项是 `{0x00,0x00}` = STANDBY ⇒ 写完必须显式补 `0x02`。

**对 T206 设计的后果（重要）**：

- §5.2c 的 **A 分支变成确定项**：上电后 H 组即等于金标 ⇒ `CanStart=true` ⇒ 直接 `0x01` 起流。
- ⇒ **ESP32 侧不做「START 前同步」**（原拍板⑥ 的功能前提被固件消掉了）。改为：
  `0x01` → 2 s 内无显示帧 ⇒ **重试 `0x01` 一次** → 仍无帧 ⇒ 报错（并可用 `0x10` 取快照供诊断）。

- 只有「上电写表失败」这一种残留情形才会让 H 组不一致；那时 `afe boot init:N`（N>0）会明示，

- ⚠ 与 `0x01` **互不依赖**：`ads1293_start()` 第③步照样写全表（P1 依据）。
  上电写表失败也不会让 START 坏掉，只是快照/校验环节不一致。

### 8.1 这条设计的代价（须知，非反对）

1. **START 之后就改不了模式/陷波** —— 现场若发现 50 Hz 干扰或要切诊断/监护，只能断电重来。
   （临床流程上通常是「贴电极 → 看波形 → 调参数 → 记录」，参数在 START 前定，可接受。）
2. **停不下来 = 无法"结束一次会话"** —— 将来若要「保存本次记录 / 打标记」，必须补一个
   结束动作（哪怕只是 ESP32 侧的本地停止记录，不必发 `0x02`）。
3. **ESP32 重启后的配置时机** —— 由 §5.1 的 `0x10` 探针解决，不需要给用户 STOP 按钮。

### 8.2 仍然需要的一条纪律

`0x01 START` 本身是**下行命令**，且发生在「总线上还没帧流」的窗口 ⇒ 干净。
但若用户在上电配置后手抖多点几次「开始」，会重复发 `0x01`。
`ads1293_start()` 会重走一次采集链初始化 ⇒ **波形会出现一次基线瞬态**。
⇒ START 后立刻把「开始」键置灰（不等 STA），并让 `ecg_cmd_start()` **内部只发一次**
（连发仅用于抗单次丢失，靠 `cmd_start_pending` 标志防重复触发）。

## 9 待定项：`ecg_pipeline` 的 TYPE 过滤（猛哥 11-04 16:58 挂账）

### 9.1 缺陷本身（已核到行号，不是推测）

- `ecg_frame.c:103 ecg_frame_parse_raw()` **只按 LEN 分流，不看 TYPE**（`fr->type` 取了但没人用）。
- `ecg_pipeline.c:405-416 rs485_producer_loop()`：`crc_ok` 之后**直接** `push_sample()`，无 TYPE 判断。
- ⇒ 任何 **LEN ≠ 显示帧长度** 的合法帧都会被当波形消费。`0x03` 快照帧 `LEN=74`
  ⇒ `n_total=(74-3)/2≈36` ⇒ **36 个寄存器值被当成 36 个 ECG 样本灌进环缓**。

### 9.1b 🛑 比快照更早中招的是**下行命令帧**（11-04 收尾复读码新发现）

下行帧 `AA 55 | 0x80 | LEN | CMD | ARG | CRC8`，`0x01 START` 的 `LEN=1`：

```
hdr_len = 3（odd）           // ecg_frame.c:120
n_total = (uint16_t)((1 - 3) / 2)   // :125 → int 里算得 -1 → cast uint16 = 65535
fr->n_ch1 = 65535            // :133
if (n_ch1 > ECG_MAX_SAMPLES_PER_CH) n_ch1 = 50;   // :137 靠这个 clamp 兜住，没溢出
for (i < 50) ch1[i] = le16(sp + i*2);             // :141 → 从 1 字节 payload 起读 100 B ⇒ 越界读 99 B
```

- `n_total` 在 `len < hdr_len` 时**无符号下溢**，只剩 clamp 兜底（不崩，但读垃圾）；
- **CRC 照样通过**（`crc_calc` 只用 `len`，`ecg_frame.c:150`）⇒ 下游拿到 `crc_ok == true`；
- ⇒ PC 与 ESP32 **并挂同一条 485** 时，PC 每发**任何一条**下行命令，
  ESP32 屏上就多 **50 个垃圾样本**（含 `0x01 START` 那一条）。

⚠ 这一条把「TYPE 过滤」的性质从"防快照污染"改成了"**并挂方案的硬前置**"。
规避手段（不改代码）：**让 producer 晚于命令启动** —— 先由 PC 发 `0x01`，
再在 ESP32 上敲 `485-start`（`rs485_init()` 里有 `uart_flush`，`rs485_port.c:108`，会清掉残留）。


### 9.2 为什么现在可以不改（猛哥的判断成立）

T207 落地后，**正常业务路径上不会再出现 `0x03`**：

| 场景 | 会不会有非 0x01 帧流入 | 要不要改 |
|---|---|---|
| ESP32 独立成机，只收波形（`0x01` 由 ESP32 自己发） | 不会 | **不用改** |
| ESP32 发 `0x10 REQ_SNAPSHOT` 探针（判断 RUN/STOP） | **会**（0x03 快照，36 个假样本） | **必须改** |
| ESP32 发 `0x03 RESET`（一条命令＝复位+写表+回快照） | **会**（同上） | **必须改** |
| **PC 与 ESP32 并挂同一条 485**（今天这种过渡接法） | **会**（每条下行都中招，见 §9.1b） | **必须改**，或用 §9.1b 的启动顺序规避 |

⇒ 一句话边界：**这套设计（§5.2c 分支 A + T207）里，唯一会让快照帧回到数据流的就是「探针/复位」**。
只要 ESP32 侧不发这两条，TYPE 过滤就是纯防御，可以挂账。

### 9.3 但如果将来加了探针 —— 改法只有 1 行

```c
/* ecg_pipeline.c:405 */
if (!fr.crc_ok || fr.type != ECG_TYPE_DISPLAY) {
    continue;
}
```
（`ECG_TYPE_DISPLAY` 建议在 `ecg_frame.h` 补一个宏＝`0x01`，别裸写数字。）

### 9.4 不做的话，失配那天长什么样（便于届时快速定位）

- 屏幕出现**一串等间隔的台阶/跳点**，样本数每帧恒定多出 ~36 个；
- BPM 被拉高甚至乱跳，但 `crc_errors` 仍为 0、`frames` 正常涨 —— **指标全绿、波形是错的**；
- 只在「发了 `0x10` 或 `0x03` 之后」出现，`485-start` 重启后消失。
⇒ 见到这个组合，**先怀疑 TYPE 没过滤，不要先怀疑链路或 AFE**。

### 9.5 同批挂账的另一项：`485-send <hex...>`

`cli_console.c` 命令表（`:1300-1420`）里**没有任何下行发送命令** ⇒ ESP32 当前只能收不能发。
这决定了「ESP32 能不能自己把 STM32 跑起来」：不能。
⇒ 若采用「PC 与 ESP32 并挂同一条 485 总线、由 PC 发 `0x01`」的过渡方案，可暂不加；
  若要求 ESP32 **独立成机**（上电自跑），这条是前置条件，必须在接通当天落地。

- 🛑 **不设 STOP 键**（拍板⑤）；要停走 CLI `485-send stop`。
- 🛑 点完置灰的理由：`0x01` **不幂等**，`ads1293_start()` 首步停流重走采集链（`ads1293.c:843`）⇒ 重发会留一次基线瞬态。
- 用 `s_capture_started` 这个**本机标志**驱动显示，**不读** `ecg_pipeline_running()` —— 485 生产者从 `485-start` 起就常驻，running 恒 true，判不出"STM32 是否已出数据"。采集真值只看帧流与 `STA`。

### 10.4 CLI（`cli_console.c`）

```
485-send start     ≡ 点屏上「开始」（发 0x01，整帧 AA 55 80 01 00 01 5D）
485-send stop      本设计唯一的停机入口（发 0x02，整帧 AA 55 80 01 00 02 54）
485-send           只打印用法，一个字节都不发
```

🛑 **不提供"原样发十六进制"**（猛哥 11-04 17:44 拍板）：它与 `start` 发的是同一串字节，
多一条入口只多一处误用面；而"CRC 到底有没有在校验"不需要造坏帧去试 —— 见 §10.5 的统计量判据。

### 10.5 验收步骤（接上硬件后照这个走）

1. `485-start` → 屏上「开始」由灰变亮（CLI 里已加 `ui_button_bar_refresh()`，不必等别的动作）。
2. `485-stat` → `rx=0 B frames=0`（**此时正常**：STM32 停在 STOP，不发帧）。
3. 点「开始」（或 `485-send start`）→ 按钮变灰显示「采集中」。
4. `485-stat` → `frames` 开始涨、`crc_err=0`、`seq_gaps=0`；屏上出波形。
5. **异常怎么读**（替代"造坏帧"的判据，全部在 `485-stat` 一行里）：

| 现象 | 指向 |
|---|---|
| `frames` 涨、`crc_err` 也涨 | 线路质量 / 波特率偏差 / A-B 干扰 —— 硬件侧 |
| `resync` 大、`frames` 很小 | 帧头对不上（多半是余一个字节或半个包 ⇒ 检查发送端是否加了 CR/LF） |
| `bad_len` 涨 | LEN 字段与实收长度不符（发送端拼帧错） |
| `frame` / `parity` 涨 | UART 层帧错/校验错 ⇒ 波特率、地、终端电阻 |
| 全为 0 但无波形 | **别再怀疑 CRC**：STM32 根本没 START，或根本没接上 |

### 10.7 真机验证（11-04 18:57）

**ESP32 下行通道已验证通过**：把 A/B 接到 PC 的 USB-485（COM27）后，

同时确认：

| 方向 | 状态 | 依据 |
|---|---|---|
| ESP32 → 总线 | ✅ | COM27 收到完整 START 整帧 |
| 总线 → ESP32 | ✅ | `rx=640 B`（STM32 复位后的 ASCII 横幅，`resync=640` 属正常） |

🛑 **复测前提：总线上只能有一台 485 设备对应 STM32 那一侧。**
PC 的 USB-485 与 UT-2211 **同时并挂**时，两个 120 Ω 终端并联 + 两套偏置网络会互相压制，
`tx` 计数照涨但对端收不到 —— 这是本轮最可能的干扰源。

⚠ 诊断口径（本轮两次误判的教训）：
- `tx_bytes` 是**软件计数**（`rs485_port.c:150`，`uart_wait_tx_done` 返回值被忽略），**不能用来判断"是否上了总线"**；
- 判二进制收发必须用 **HEX 视图或脚本抓原始字节**（`485tools/tools/probe_com27.py`），
  文本模式显示 `AA 55 80…` 必然是乱码，别把乱码当失败。
