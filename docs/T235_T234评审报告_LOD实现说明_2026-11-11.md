# T234 评审报告：LOD 导联脱落检测实现说明

> **日期**：2026-11-11；**修订**：2026-11-12（v1.1，纳入作者逐条复核）  
> **评审对象**：`T234_LOD导联脱落检测实现说明_2026-11-11.md`  
> **评审依据**：T232、T233、当前 STM32/ESP32 源码、ADS1293 数据手册、AECG100 用户手册  
> **评审结论**：**当前台架实现可有条件接受；T234 需订正关键机制表述；产品级 LOD 尚未放行。**

---

## 0 总体结论

T234 已较完整地描述：

- ADS1293 DC LOD 原理；
- STM32 寄存器配置、低频轮询、软件锁存和非对称防抖；
- STA bit4 从 STM32 到 ESP32 的传递；
- ESP32 导联状态图标；
- 台架接线、真实通道语义和实测结果；
- 停流、快照和显示防抖等已知边界。

当前实现和台架结果支持：

- `0x06=0x00`：DC LOD 工作；
- `0x07=0x07`：检测 IN1~IN3；
- `0x08=0x01`：8 nA 注入电流；
- 20 ms 低频读取、60 ms 置位、500 ms 清除；
- 拔 IN1/IN2/IN3/IN4 均可触发 STA bit4；
- IN3 脱落时 QRS、BPM 可继续；
- IN4 回流断开时三路全报；
- 台架置位约 0.4~1.6 s、恢复约 0.6~1.8 s。

但 T234 作为“LOD 机制权威说明”仍有以下问题：

1. `ERROR_LOD` 锁存语义写反；
2. SPI 持续读取失败后没有 LOD 状态健康判据；
3. “任意 LOD”与“CH1 是否有效”的产品语义尚未冻结；
4. 端到端只传汇总 bit；是否要求分路上报属于产品范围决策；
5. 停流后图标状态的错误描述实际位于 T232 §17.1，不是 T234；
6. 产品级空载、信号切换、C-3 联动和人体测试尚未闭环。

因此，本次评审结论分为三层：

- **当前 T234 台架实现**：可有条件接受，可继续受控测试；
- **T234 文档表述**：需要订正；
- **产品放行**：不通过，仍需独立产品验证和安全评审。

## 1 已认可的内容

### 1.1 寄存器配置正确

当前代码如下：

```c
#if ECG_LOD_EN
    {0x06, 0x00},   /* DC LOD 工作 */
    {0x07, 0x07},   /* IN1、IN2、IN3 */
    {0x08, 0x01},   /* 8 nA */
#else
    {0x06, 0x08},
    {0x07, 0x00},
    {0x08, 0x00},
#endif
```

与 ADS1293 手册一致：

- `SHDN_LOD=0` 才工作；
- `SELAC_LOD=0` 为 DC 模式；
- `0x07=0x07` 启用 IN1~IN3；
- `0x08=0x01` 为8 nA最小非零档；
- `0x12[2]=1` 满足错误寄存器更新所需时钟；
- `0x2E=0x33` 为默认比较器计数配置。

### 1.2 IN4 不参与 LOD 是正确的

`RLD_CN=0x04` 表示 `SELRLD=100`，将 RLD 输出内部路由到 IN4。

因此：

- IN4 本身是模拟输入脚，但本设计通过 `SELRLD=100` 把 RLD 输出并接其上，
  因此当前不应把 IN4 作为普通导联输入参与 LOD；
- `0x07=0x0F` 会错误启用 IN4；
- `0x07=0x07` 是当前合理配置；
- IN4断开时通过“回流消失、IN1~IN3全报”体现。

该机制与手册中“无低阻回流时所有启用输入均报告脱落”的要求一致。

### 1.3 低频读取 + 软件锁存方向正确

把 `0x18` 从逐样本路径移除，改为20 ms轮询，可减少 SPI 开销，并保留硬件锁存事件。

软件状态机的非对称设计合理：

```text
置位：连续3次非零，≥60 ms
清除：连续25次为零，≥500 ms
```

单次读取失败保持现状，单次零值不立即清除，避免接触抖动导致状态频繁翻转。

### 1.4 台架验证已形成关键证据

现有台架结果支持：

- 8 nA 足以在约2 s内检测开路；
- IN1/IN2脱落会使当前 CH1 的 QRS 停止；
- IN3脱落可报警而 CH1 继续；
- IN4回流脱落会导致三路全报；
- LOD 回路建立后，AECG 差分信号可以继续存在。

这些结果足以支持继续开展受控台架验证。

## 2 P0 级问题

### 2.1 [P0] `ERROR_LOD` 锁存语义写反

T234 §1.5 与 F-6 写道：

> 错误在读之前已消失，读回来是0，这次事件就永久丢了。

该表述与 ADS1293 手册不符。

手册 §8.3.27 明确：

- 错误位一经发生即锁存为1；
- 只有读取后才清零；
- 若故障持续，读后还会重新置1。

正确过程：

```text
故障发生
   ↓
硬件锁存位=1
   ↓
即使故障已消失，下一次读取仍得到1
   ↓
读取后清零
```

因此：

- 20 ms低频读取不会丢失读取之间的短事件；
- 软件锁存仍用于维持告警和防抖；
- “删去逐样本读取”不需要以“防止事件永久丢失”为理由。

当前代码逻辑可以保留，但 T234 的机制说明和 F-6 必须订正。

### 2.2 [P0] SPI持续失败没有状态健康判据

当前逻辑：

```c
if (ads1293_read_reg(...) != HAL_OK) {
    return;
}
```

单次失败保持状态是正确的，但持续失败会带来：

- 原状态为正常时，永久显示“正常”；
- 原状态为脱落时，永久显示“脱落”；
- ESP32 无法区分“真实状态”与“STM32 LOD读取已失效”。

建议增加：

```text
last_ok_ms
consecutive_fail_count
LOD_STATE_FRESH / STALE / UNKNOWN
```

规则建议：

- 单次失败：保持状态；
- 连续失败超过500 ms：状态变为“未知/设备状态异常”；
- 不得继续把陈旧状态当作实时LOD。

**不得复用 STA bit4 表达“状态不可信”。** bit4 已冻结为“任意启用输入脱落”；
如果 SPI 失效也置 bit4，会破坏现有图标、上位机和未来 C-3 门控语义。

建议新定义：

```text
STA bit4 = 任意启用输入脱落
STA bit5 = LOD_STALE（读取失效，bit4值不可信）
```

bit5 需要协议版本升级和 ESP32/WinApp 同步修改。若暂不扩协议，另一个保守选项是
SPI 连续失败时强制 bit4=1，但这会把“设备 LOD 读数失效”混同成“导联脱落”，
只能作为明确接受误报代价的临时安全策略。

还要区分两类陈旧：

- **帧流陈旧**：停流后没有显示帧，`has_sta` 无法自动复位；
- **LOD 读取陈旧**：显示帧持续存在，但 STM32 的 LOD 轮询持续失败。

两者是不同故障，不能共用同一判据。

### 2.3 [P0] QRS/BPM 联动语义未冻结

当前仅实现“导联状态图标”，未实现：

- LOD置位 ⇒ 抑制R峰；
- LOD置位 ⇒ BPM立即失效；
- LOD置位 ⇒ 停止HRV更新。

T234已明确说明这一点，但仍需定义产品规则。

当前事实：

```text
CH1 = IN2 − IN1
```

因此当前CH1的直接有效性至少依赖：

```text
IN1连接 AND IN2连接
```

但还需考虑：

- IN3/地端脱落是否影响真实人体共模；
- IN4/RLD回流脱落时，台架差分信号继续，但真实人体CMRR和信号质量可能恶化；
- 是否读取 `RLDRAIL`、`CMOR` 和输入饱和状态；
- 红色导联叉出现后，BPM继续显示是否会让用户误判。

建议至少定义两套状态：

```text
LEAD_ALERT：存在导联/回流异常，但当前QRS通道可能仍有效
MEASUREMENT_INVALID：当前QRS通道不可用，停止打点和BPM
```

但必须明确依赖关系：

> **当前 STA bit4 是任意输入脱落，无法区分 IN1/IN2 与 IN3。
> 因此当前协议只能定义上述语义，不能可靠实现选择性门控。**

在当前协议下若直接用 bit4 门控，会出现：

```text
拔 IN3（CH1 仍有效）⇒ bit4=1 ⇒ 错误停止 QRS/BPM
```

所以 C-3 有两个可行方向：

1. 保守门控：任意 LOD ⇒ 停止测量，接受 IN3 导致停测；
2. 扩协议上传逐输入位后，再实现按 CH1 有效性门控。

不能长期停留在“显示红叉但BPM仍作为有效值展示”的无定义状态。

### 2.4 [P1] 分路上报属于产品范围决策

ADS1293 提供 `ERROR_LOD[5:0]`，STM32内部也保留逐输入位。

但当前二进制协议只传 STA bit4：

```text
bit4 = 任意输入脱落
```

所以端到端能力是：

> “是否存在任意脱落”，不是“具体哪一根脱落”。

T234 中的“分路可区分”主要依靠观察 QRS 是否继续来间接验证，不能等同于 ESP32
或上位机已经收到 IN1/IN2/IN3 状态。

必须如实写成：

- AFE/STM32内部：逐输入状态可用；
- 当前帧协议：仅汇总状态；
- ESP32：只能显示“有脱落”；
- 分路显示：当前未实现。

**范围裁定：**

- 若本轮产品需求只是“任一路脱落则提示”，当前汇总 bit 已满足；
- 若产品要求“指出哪根掉了”或“IN3 脱落不禁用 CH1”，分路上报才是必须项；
- 这个范围未拍板前，不应把分路上报无条件列为所有产品的放行阻断。

## 3 P1 级问题

### 3.1 ALARM_FILTER计数少算一次

手册规定计数为编程值加1。

因此 `0x2E=0x33`：

```text
AFILTER_LOD=3
实际计数=3+1=4
4 × 2.44 µs ≈ 9.8 µs
```

手册描述这些数字时钟在 409.6 kHz 时钟下降沿翻转；若“数字周期”按二分频后的
完整周期计，则可能是 `4 × 4.88 µs ≈ 19.5 µs`。因此应写区间：

```text
约 9.8~19.5 µs
```

而不是 T234 §1.4 写的 3 次、约7.3 µs。

结论“硬件防抖只有微秒级，软件防抖仍必需”不变，但数值应订正。

### 3.2 软件锁存应限制到已启用输入

建议定义统一宏：

```c
#define ECG_LOD_MASK 0x07u

s_lod_latched |= (raw & ECG_LOD_MASK);
```

理由：

- 当前仅启用IN1~IN3；
- 防止配置切换或残留位影响汇总状态；
- STA bit4的实际语义应严格为“已启用输入中任意一路脱落”。
- 避免 `regs_leaderIII` 和锁存位各写一套魔数。

### 3.3 停流后图标状态文档矛盾

T234 §7.1 明确写：

> 停流后图标保持最后一帧状态。

但 **T232 §17.1** 的状态表又把“停流后”归入 `has_sta=false` 的未知状态。
T234 本身没有 §17，原评审引用文件错误。

源码实际行为：

- `has_sta` 仅由显示帧更新；
- 停流时没有路径把它复位为 false；
- 因此图标保持最后一次状态。

应统一为：

- 首次数据到达前：未知；
- 正常数据显示期间：实时LOD；
- 停流/快照期间：最后一次已知状态；
- CLI通过帧龄判断陈旧；
- UI不使用帧龄，已拍板接受保留最后状态。

### 3.4 UI状态没有“LOD状态陈旧”概念

CLI有 `距更新 X s`，但UI的 `ico_sync()` 只判断：

```text
has_sta && bit4
```

因此停流后红叉或亮灰会一直保留。

该行为已被产品决定接受，但文档必须明确：

> 图标表示最后一次收到的LOD状态，不保证当前仍为实时状态。

否则用户可能把陈旧显示误判为实时状态。

### 3.5 当前验证覆盖仍不完整

T234已诚实列出：

- LOD-ON空载30 min未完成；
- AECG100输出开启状态的完整时序未覆盖；
- C-3联动未实现；
- 真实人体未验证。

已完成的台架结果不能直接推导为产品级完成。

### 3.6 `ERROR_STATUS(0x19)` 与 `ERROR_LOD(0x18)` 的锁存行为不同

手册明确：

- 对 `ERROR_LOD` 等错误寄存器，若故障仍在，读取后会在几个内部时钟周期内重新置位；
- `ERROR_STATUS` 的位只响应**新错误**；
- 读取 `ERROR_STATUS` 后，若故障持续，它不会仅因持续存在而重新置位。

因此将来若用 `0x19 bit1=RLDRAIL`、`bit0=CMOR` 做冗余校验，不能把
20 ms 轮询结果直接当作持续故障状态。应把它们定义为事件位，并由软件保持，
或通过 ALARMB/新事件机制处理。

### 3.7 “8 nA 物理充电导致 0.4~1.6 s 延迟”仍是假说

T234 §5.1 的净充电电流模型具有解释力，但尚未直接测量。

建议做电流扫描：

```text
0x01 = 8 nA
0x08 = 64 nA
0x10 = 128 nA
```

每档至少测5次置位延迟。

- 若延迟近似按 `1/I` 缩短，则充电模型成立；
- 若延迟基本不变，瓶颈可能在比较器、ALARM_FILTER、电极极化或回路阻抗。

这个实验同时回答“8 nA 是否有必要升档”。

## 5 最终意见

### 接受

- 接受当前STM32 LOD寄存器配置；
- 接受20 ms轮询、软件锁存和非对称防抖；
- 接受STA bit4的“任意启用输入脱落”语义；
- 接受ESP32三态导联图标；
- 接受已完成台架检出、恢复和回流验证。

### 必须修正

1. 纠正 `ERROR_LOD` “读前消失即丢失”的错误描述；
2. 增加SPI读取失败的STALE/UNKNOWN处理，使用独立状态位，不复用bit4；
3. 先冻结“任意LOD停测”还是“选择性门控”的产品策略；
4. 明确端到端只上报汇总bit；分路是否扩协议由产品范围决定；
5. 修正 T232 §17.1 的停流状态描述，而不是错误地改 T234 §17；
6. 修正 ALARM_FILTER 为4计数、约9.8~19.5 µs；
7. 用统一 `ECG_LOD_MASK` 宏约束寄存器表和软件锁存；
8. 将 `ERROR_STATUS` 定义为事件位，不能按持续故障状态轮询；
9. 保留“8 nA 充电模型是假说”的表述并安排电流扫描验证。

### 一句话结论

> **T234可以作为当前LOD台架实现的技术基线，但“机制权威说明”必须订正；当前可继续受控台架验证，不能据此关闭产品级LOD。**
