### §1.1 `comm_port.c` 的三个设计点（都是踩过的坑）

1. **`comm_send` 内部拷贝，不把调用方指针交给外设。**
   `ads1293.c:1281` 的主通路缓冲是**栈局部** `char buff[512]`，而 `HAL_UART_Transmit_IT`
   与 `CDC_Transmit_FS` 都是异步取数据 ⇒ 直接交指针会让外设在函数返回后读**已复用的栈**
   （技能 §4.48 / §4.126）。拷贝 59 B 相对 5.12 ms 占线可忽略。
   ⇒ 顺带好处：**不用去改 `ads1293.c` 的缓冲声明**，改动面更小。

2. **忙判必须在拷贝之前**（`comm_port.c` 里 `if (s_tx_busy != 0u)` 在 `for` 之前）。
   顺序挪一下就变成"先覆盖掉在途缓冲一半，再判忙"（技能 §4.129）。

3. **接收用 `HAL_UARTEx_ReceiveToIdle_IT`，不用逐字节自己拼帧。**
   上位机 `SerialPort.Write()` 是**整帧一次写出** ⇒ 一次 IDLE = 一条完整命令，
   语义与 USB CDC 的"一包一次回调"完全一致 ⇒ `vcom_recv_analysis()` 零改动。
   收落点与发布区**两级分离 + 乒乓两片**（`s_rx_work` / `s_rx_pub[2][128]`），
   避免主循环读到一半被下一包撕开。

**中断优先级**：UART5 抢占优先级 **1**，DRDY 的 `EXTI1` 是 **0** ⇒ 串口打不断采样。

### 2.5 体积变化逐项归因（同工具链对照构建，不是引历史数）

`UserRxBufferFS` 与 `UserTxBufferFS` 各 **2048 B**（`usbd_cdc_if.h:52-53`）。
UART5 模式下 `MX_USB_DEVICE_Init()` 不被调用 ⇒ `USBD_Init` 整条引用链断裂 ⇒
**链接器把整个 USB 设备栈剔除**。map 实测：`hUsbDeviceFS` / `UserTxBufferFS` /
`UserRxBufferFS` / `USBD_Init` **全部 0 命中**；只剩 `hpcd_USB_OTG_FS` 与
`HAL_PCD_IRQHandler` 被 `OTG_FS_IRQHandler` 这个强符号吊住。

RAM 账：`读写数据` UART5 比 USB 少 **5023 B**，其中新增 `comm_port.o` 占 **1114 B**：

| 符号 | 字节 |
|---|---|
| `s_tx_buf` | 576 |
| `s_rx_pub[2][128]` | 256 |
| `huart5` | 136 |
| `s_rx_work` | 128 |
| 4 个计数器 | 16 |
| `s_rx_pub_idx` / `s_tx_busy` | 2 |

⇒ 被剔除的 USB 栈 RAM ≈ 5023 + 1114 = **6137 B**（4096 是那两个 CDC 缓冲）。

**USB 模式下 `读写数据` 只比基线 +8 B**（4 个计数器 16 B 大部分落进了原有 padding）
⇒ **USB 老路径的行为面没有实质变化**。

## §4 已知边界（别把这当成"全通"）

1. **ASCII-1 档在 115200 下带宽不够。**
   `_popoutcnt=5` ⇒ 100 帧/s × 约 240 B ≈ **24 kB/s**，而 115200 8N1 只有 **11.52 kB/s**
   ⇒ 会撞 `comm_tx_drops` 大量丢帧。**本轮只保证二进制档可用**（20 帧/s × 59 B = 1180 B/s = 10.2%）。
   ASCII-1 要用就把波特率提到 ≥250000（UT-2211 与适配器都得支持），另立一档。

2. **`raw853 on` 与 ASCII 档叠加时另有风险**，未测。

3. **`comm_tx_drops` / `comm_tx_frames` / `comm_rx_events` / `comm_rx_loss` 四个计数器**
   目前只能在 ST-LINK 的 watch 窗口看，**没有 ASCII 回显命令**。要不要加一条
   `test comm` 命令把它打出来（可用于实测定点丢帧），**待猛哥拍板**。

4. **USB 老路径没有回归上板**。本轮只做到"编译通过 + 体积账 +8 B"，
   要在 USB 上再验一次得把宏切回 `ECG_COMM_PORT_USB` 重烧（见下）。

5. **`OTG_FS_IRQHandler` 仍留在中断表里**（引用 `hpcd_USB_OTG_FS`），导致 PCD 相关代码
   没被完全剔除。它是死引用、不可达（`HAL_NVIC_EnableIRQ(OTG_FS_IRQn)` 在 `HAL_PCD_Init` 里，
   不会被调用）。若想再省几十 B，可用 `#if` 把它一起包掉 —— 本轮**不做**，避免动 CubeMX 生成的 ISR。

6. **没有做上位机回归的离线回环断言**。`Protocol.cs` 那边本来就是按 `AA 55` 重同步，
   混入 ASCII 是常态（运行期命令回显一直是 ASCII）⇒ 加横幅不会破坏它，但**没跑过**。

### 6.2 🛑 根因：`PD2` 的 `GPIO_PULLUP`

**`UART5_RX`（PD2）配 `GPIO_PULLUP` ⇒ 静态电位被压在 ~0.7 V，低于 STM32 输入高阈值
（0.4×VDD = 0.72 V）⇒ UART 永远读成低电平，等不到帧起始，一个字节都收不到。**

机制：引脚内部 40 kΩ 上拉到 VDD(1.8 V)，与**模组内部 `PA12`（USB D+，与本脚同网络
`RXD-USB_DP`）的 ESD 二极管**（参考端 `VDDUSB`）形成分压 ⇒ 稳态停在 ~0.7 V。

**外部线路本身是高阻**：断电量 CN9.2 对 GND > 3 MΩ（20 MΩ 档显示 3.xx）——
所以**不是外部下拉造成的**，这一点曾把我们带偏很久。

**对照验证**：`C:\work_qianya\guangpu\backup\stm32ch3020demo-iar`
（CubeMX 生成，同 UART5 / 同 PD2·PC12 / 同 AF8 / 115200）用的是 **`GPIO_NOPULL`**，收发正常。

⇒ **改为 `GPIO_NOPULL`，并在 `comm_port.c` 注释里写明"别再加回上拉"。**

### 6.4 同时修掉的第二个缺陷：UART 错误后不恢复接收

HAL 的顺序是：**先 `UART_EndRxTransfer()`（只要 errorcode 含 NE|FE|ORE 就终止接收），
再调 `HAL_UART_ErrorCallback`**。原 `comm_port.c` 没有实现这个回调 ⇒ **一次噪声/一个 break
就让接收永久失聪**（这正是 `rx_events` 恒 0 的直接原因之一）。

已补：清 `ORE/FE/NE/PE` 标志 → `RxState` 拉回 `READY` → 重挂
`HAL_UARTEx_ReceiveToIdle_IT`，每次失败 `comm_rx_loss++`（不静默）。
⚠ USB 模式永远不会暴露此缺陷（CDC 无 break 概念），故此前未发现。

### 6.5 🛑 方法坑：读寄存器必须用 `mode=hotplug`

`STM32_Programmer_CLI -c` 默认 `Reset mode: Software reset`，会先复位目标，
此时读到的是**复位尖峰期的空白状态**（曾误读成 `UART5_CR1=0`、`RCC_APB1ENR1=0`、`VTOR=0`，
一度误判"固件没跑到 `comm_init`"）。**必须加 `mode=hotplug` 才是运行态。**

### 6.7 接线定案（原理图实证，勿再动摇）

UM2101 §焊桥表的列序在 PDF 文本提取时错乱，**以 Figure 22 原理图图形为准**：

```
CN9.1 = UART_RX 网络 = CC7(pin13)↔L7(pin8) = SB20 = TXD-USB_DM = PC12 = STM32 TX（输出）
CN9.2 = UART_TX 网络 = CC5(pin15)↔L5(pin6) = SB11 = RXD-USB_DP = PD2  = STM32 RX（输入）
```

- 焊桥是**两组二选一**：`SB11`(RXD→上汇流线) / `SB21`(TXD→上汇流线)；
  `SB10`(RXD→下汇流线) / `SB20`(TXD→下汇流线)。
  🛑 **SB11+SB10 或 SB21+SB20 同时焊会把同一根模组信号引到两个 CN9 脚、另一根悬空 ⇒ 收发断一路。**
- 合法组合：`SB11+SB20`（当前）或 `SB21+SB10`（仅把 TX/RX 在 CN9 上互换）。
- **接线按信号方向**：`CN9.1 → 适配器 RXD`、`CN9.2 ← 适配器 TXD`、共地、**3.3V TTL**。

## §7 完整 485 链路验证（T203）与第④步为何取消

### 7.1 链路与结果

```
ADS1293 + STM32L476 ─UART5─→ TTL转232 ─→ UT-2211(232↔485) ─→ 485转USB ─→ PC
                                                                        └─ WinApp 出 AECG100 波形 ✓
```

- **双向均通**：WinApp 的 START 命令能下发（`comm_rx_events` 恰好 +1），AECG100 波形能上传。
- **上行零丢帧**：15 s 内 `comm_tx_frames` 41 → 624（583 帧），`comm_tx_drops` 3 → 3 不变。
  ⚠ **订正（见 §8.4）**：这里的「15 s」是估的，实际跨度约 29.7 s。583 帧按实测
  19.6 fps 折算正好对上，帧率本身**没有**偏高。`comm_tx_drops` 不变这一条仍然成立。

### 7.2 关键对比：TTL 直连 vs 485 差分

同一套固件、同一条上行负载（满速采集），只换传输介质：

| 链路 | `comm_rx_loss` 速率 | 判读 |
|---|---|---|
| TTL 直连（CN9 → USB 转串口） | **3.6 次/秒** | 线缆共模干扰串进 `PD2` |
| TTL转232 → UT-2211 → 485转USB | **0 次 / 15 s** | 差分传输把它抑制掉 |

**结论：之前那 3.6 次/秒是线缆上的共模干扰，不是模组内部 `PC12`→`PD2` 的耦合。**
⇒ **不需要外部上拉、也不需要飞线换串口**，两项硬件改善方案作废。

### 7.3 第④步（拔线反证）为何取消

- **原意**：切断信号源看波形是否消失，排除"WinApp 显示缓存 / 循环重绘 / 别的数据源"这类假数据。
- **被判据更强的做法替代**：实测**波形随 AECG100 的设定变化而变化** —— 这是「输入改变 ⇒ 输出跟着变」的因果验证，直接证明了实时采集链路的真实性，比"有东西在动 / 没东西在动"强得多。
- 另：WinApp 代码里没有 replay 功能，原有假设本身就不成立。

⚠ **但这条判据依赖"有可调输入"**。若换到无法改变输入的场合（例如只观察本底噪声），
"拔线看现象是否消失"仍是必要的阴性对照，**不能因为这次取消就把它从规程里删掉**。

## 8. 下行命令验证（T204，2026-11-03 17:2x）

### 8.1 结论

**WinApp 的「工况」与「陷波」两个开关，在 485 链路上完全可用。** 四条命令全部生效，
半双工转换器的方向抢占**未发生**。

| 下发命令 | 下行帧（8 B） | 之后 STA | 解析 | 判定 |
|---|---|---|---|---|
| SET_NOTCH(关) | `AA 55 80 02 00 05 00 FA` | `0x00` 诊断·陷波关 | notch=0 ✓ | **PASS** |
| SET_NOTCH(开) | `AA 55 80 02 00 05 01 FD` | `0x02` 诊断·陷波开 | notch=1 ✓ | **PASS** |
| SET_MODE(监护) | `AA 55 80 02 00 04 01 E8` | `0x03` 监护·陷波开 | mode=1 ✓ | **PASS** |
| SET_MODE(诊断) | `AA 55 80 02 00 04 00 EF` | `0x02` 诊断·陷波开 | mode=0 ✓ | **PASS** |

命令字节与上位机 `Core/BinCommand.cs:110-113` 的编码器逐字节一致（CRC8 覆盖
TYPE+LEN+CMD+ARG，poly=0x07/init=0x00/不反射），离线对拍过 5 帧。

### 8.2 判据为什么必须是 STA，不能是「点了没报错」

`Form1.cs:744-765` 点击后先调 `MarkSelectionOptimistic()` 落**乐观高亮**，再发帧；
`RefreshCommandUi()` 里一旦 `displayFrameCounter` 变化（即**下一帧显示帧到达**）
就把乐观值撤销、回落到 STA（`Form1.cs:1809-1813`）。

⇒ **高亮在 ~50 ms 后弹回 = 没生效**；稳住 = 生效。状态栏那格
`statusStripSta.Text = DisplayFrame.Describe(lastFrameSta)`（`Form1.cs:2037`）
**纯 STA 派生、无乐观值**，是更干净的读数点。

固件侧这条链零改动，逐行核过：

```
UART5 IDLE 中断 → HAL_UARTEx_RxEventCallback (comm_port.c:213)
  → vcom_recv() 只存指针/长度
  → 主循环 vcom_recv_analysis() (vcomcmd.c:824)，前两字节 AA 55
  → vcom_bin_dispatch() (vcomcmd.c:606)
  → case 0x04 (:706) / case 0x05 (:727) ⇒ ecg_filter_f64_set_*
```

两条命令都**不加状态门**、`argLen` 必须 == 2；回执是**下一帧的 STA 位**，不是回帧。

### 8.3 方法：`stm32/tools/_t204_cmd_probe.py`

脱离 WinApp 的字节级探针（WinApp 关掉后可跑），按「陷波关 → 陷波开 → 监护 → 诊断」
顺序发命令，每步**按帧数**收 25/60 帧再判，输出逐条对账表。

```
python stm32/tools/_t204_cmd_probe.py --port COM27 --frames 60 --repeat 3
python stm32/tools/_t204_cmd_probe.py --port COM27 --start      # STOP 态先起流
```

⚠ **当前口是 COM27**（CH340，485 转 USB），不是早前记录的 COM9 —— 端口枚举已变。

### 8.4 顺带销案：帧率「偏高 25%」是测量误差

§7.1 记的「15 s 内 583 帧」曾被推成 24~26 帧/s、怀疑偏高 25%。**这是错的**，实测：

| 测法 | 帧数 | 实测跨度 | 帧率 | 样本率 |
|---|---|---|---|---|
| 逐字节打点（1 B 一次 read） | 98 | **4.949 s** | **19.60 fps** | **495.0 Hz** |
| 探针 collect（64 B 一次 read） | 60 | 3.00 s | 19.64 fps | 491.1 Hz |

理论值：`500 Hz ÷ 25 样本/帧 = 20 fps`。实测 **19.6 fps / ~495 Hz** ⇒ **正常，无异常**。
帧间隔中位 **50.13 ms**（直方图 83/98 落在 50±1 ms）。

⇒ **§7.1 的「15 s」是估出来的窗口，实际跨度约 29.7 s**（583 ÷ 19.6），不是 15 s。

### 8.5 🛑 测量坑：CH340 上 `read(n)` 的超时语义不可靠

**现象**：探针第一版用「读满 1.5 s」当窗口，报出 **46.0 fps**（偏高 2.3 倍）。

**根因**：`port.read(4096)` 在 CH340 驱动上实测阻塞到 **3.49 s**（不是标称的 0.1 s
字符间超时）⇒ 帧数照收、分母却按 1.5 s 算。

**纪律**：

1. **凡要算速率，分母必须取「首帧与末帧的实测到达时刻差」**，不能用标称窗口秒数。
2. **一次 read 里解析出的多帧会共用同一个时间戳** ⇒ 批量读会压缩跨度、抬高帧率。
   要测帧率就把 chunk 降到一帧大小（64 B）或逐字节。
3. 判 PASS/FAIL 用**帧数**驱动（收够 N 帧再判），不要用时间驱动 —— 帧数不受这些
   OS/驱动缓冲行为影响。
