# T236 LOD bit5 回归测试清单（2026-11-12）

> **被测改动**：2026-11-12 那批 —— ① `ECG_LOD_MASK` 单一真源 ② **新增 `STA.bit5 = CH1_INVALID`**
> ③ ESP32 `485-stat` 增加 `ch1inv` 显示
> **范围**：ADS1293 + STM32 → RS485 → ESP32（模拟真机台架）。
> 🛑 **本轮不测**：WinApp 全部；ESP32 门控动作（未实现）；CH2 数据正确性（`CH2≡CH1` 未变）。
> **性质**：回归 + 新功能验收。**任一组 FAIL 即停止后续组**，先定位。
>
> 相关文档：机制见 `T234`（§2.6 bit4/bit5、§2.7 回流、§5 时序）；历史用例见 `T232` §16。

## 1 期望值速查（**先记住这三组字节**）

| 工况 | `raw` STA | bit4 `lod` | bit5 `ch1inv` | 屏上 | QRS 打点 |
|---|---|---|---|---|---|
| 全接好 | **`0x02`** | 0 | 0 | 亮灰 | 正常 |
| **只拔 IN3** | **`0x12`** | 1 | **0** | 红叉 | **继续** |
| 拔 IN1 / IN2 / IN4 | **`0x32`** | 1 | **1** | 红叉 | 停 |

> `0x02` 里的 bit1 是 **notch=on**（当前 profile 默认）。若把陷波关了，全接好应是 `0x00`，
> 其余两组同理各减 `0x02`。**测前先 `485-stat` 确认 notch 状态，别拿错基准。**

🛑 **拔 IN4（回流断）为什么也会 `ch1inv=1`**：手册 §8.3.16 规定"无回流时**所有使能脚全报**"，
所以 `s_lod_stable = 0x07`，而 `0x07 & 0x03 ≠ 0` ⇒ bit5 照样置位。
**这是预期变更**（T232 §16.3 观察到"拔 IN4 时 QRS 仍在跑"，那是"信号还在"，不是"我们信它"）。

| # | 用例 | 期望 | 实测 | 判定 |
|---|---|---|---|---|

| C2 | 置位延迟（拔 → `lod=1`） | ≤2 s（基线 0.4~1.6 s） | 补测 3 轮：**9.54 / 3.54 / 0.28 s**。⚠ 前两轮是"cue 已到、人还没动手"的人为延迟（不是设备慢）；**第 3 轮 0.28 s 才有效** | ✅（见注） |

> 🛑 **C1 判据修正（2026-11-12 11:08）**：原表写"只拔 IN1 ⇒ 只可能 `0x02`/`0x12`" **是错的**。
> 拔 IN1 会同时置 bit4（任意脱落）与 bit5（IN1 属 CH1 两路之一）⇒ 正确值域是 **`{0x02, 0x32}`**。
> `0x12` 只在**拔 IN3**时出现（B2 已验证）。
> ⇒ **C1 实质通过**（10 轮只有这两种值，说明 `ECG_LOD_MASK` 没有残留位）；
> 但 C2 因判据错而漏测，需补测。

**C2 补测实测（11:12:06/12/18 各拔一次 3 s）**：

| 轮 | 置位延时 | 说明 |
|---|---|---|
| 1 | 9.54 s | ❌ 不可用：cue 到了但人未及时动手 |
| 2 | 3.54 s | ❌ 同上 |
| 3 | **0.28 s** | ✅ 有效 |

⇒ **测法缺陷**：`cue → 人手动作` 的延迟被算进了"设备延时"。

> C1 是 `ECG_LOD_MASK` 的间接判据：若锁存里混进了 bit3 以上的位，`raw` 会出现 `0x0A`/`0x1A` 之类。

## 9 本轮执行中发现的问题（A 组，2026-11-12 10:45~10:55）

### 9-1 ✅ **已推翻**：`ch2` 本身正常，之前是我误判（2026-11-12 11:50 受控实验）

**原始误判**：A3 第一次跑时 `485-send stop` → `ch2 1` → `start` 得到 `frames=0`、`rx=0`，
连发 4 次 `start` 都无效 ⇒ 我写成"`ch2` 之后流拉不回来，阻塞双通道"。

**受控实验（同一会话，先确认源在跑）**：

| 组 | 命令序列 | 结果 |
|---|---|---|
| 对照 A | `stop` → `start`（**不碰 ch2**） | 118 → **200 帧，恢复** |
| 实验 B | `stop` → **`ch2 1`** → `start` | 118 → **421 帧，恢复** |
| 收尾 | `ch2 0` → `start` | → **537 帧，恢复** |

**再单独验 `0x06` 是否被接受**（该命令成功会回一帧快照，`snapshots` 必 +1）：

```
ch2 1 之前   snap=0
ch2 1 之后   snap=1        ← 命令被接受
start 之后   raw=0x06      ← bit2=1（I&II）
帧长         109.8 B/帧    ← 双通道成立
```

**真因**：那次会话**开头没有 `485-start`**，而 ESP32 在会话之间**重启过**（本轮实测 `uptime ≈ 125 s`）
⇒ `ecg_cmd_send()` 走 `if (!rs485_ready())` 分支直接返回 `ESP_ERR_INVALID_STATE`，命令**根本没发出去**。

🛑 **教训（比 bug 值钱）**：`485-send` **有明确回显**，例如

```
SET_CHANNEL(0x06) arg=0 -> OK   快照回执 1 帧
  ⇒ 通道 II 已关闭（后续帧长 53（单通道）、STA.bit2 跟随；run 起来后看 485-stat）
```

失败时会打 `ESP_LOGE("485 未初始化（先执行 485-start）")`。
**我忽略了这个返回值就下了"流拉不回来"的结论 —— 这是第二次犯"不看回显就归因"**（第一次在 PC 侧）。

### 9-2 每个新会话都必须重新初始化

`485-start` 内部会 `rs485_reset_stat()` 清零计数器；且新开会话后 STM32 侧不保证仍在流状态。
⇒ **每个测试会话的第一组命令固定为**：`485-stop` → `485-start` → `485-send start`。
（本次 A6 第一次跑就因为这个拿了全 0，白跑一轮。）

### 9-3 烧完 STM32 若指示灯不亮 / `rx=0`：拔插 USB

ST-LINK CLI `-P ... -Rst` 报 `Verification OK`、`MCU Reset`，但 MCU 实际**没有跑起来**
（板上指示灯不亮、链路上 `rx=0 B`）。
⇒ 拔插一次 USB 后正常。**烧录后先看灯**，别急着判"固件有问题"。
