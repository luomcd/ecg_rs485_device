## 0 三十秒决定走哪条路

| 你想干什么 | 用哪条路 | 屏幕 | 速度 | 输入序列可信度 |
|---|---|---|---|---|
| **证明板端检测器与 PC 逐峰一致** | **`mit-set` + `mit-run-all`（batch）** | 黑屏 | 全速（30 min 记录 ≈ 9 s） | ✅ **权威**：逐样本同步喂，无环缓 |
| **看波形、看增益/走纸是否正常** | **`mit-run <rec> --speed N`** | 有波形 | 1/2/4/8× | ⚠ 走 pipeline + 环缓，**可能丢样本**，必须看 `dropped=0` |

## 2 路径 A：`mit-set` + `mit-run-all`（batch，对账权威）

### 2.1 命令序列

```bat
mit-set 100,108,208          :: 写 /sdcard/batch_mit.txt；也支持 mit-set all（全 48 条）
mit-run-all                  :: 登记，提示"请重启"
restart                      :: 重启后**在 LVGL 之前**全速跑，屏幕黑屏属正常
```

`mit-set` 成功时会回读自检：`已写 /sdcard/batch_mit.txt：3 条 / 186 B（回读自检 3/3 ✓）`

### 2.2 怎么知道跑完了

串口会依次出现（**这是唯一权威的完成信号**）：

```
BATCH-BEGIN total=3
# CardioLite S7 batch: fs=500 Hz, 每行最多 16 个峰索引
FILE mit_100_500.bin frames=36112 samples=902800 bad=0 peaks=2272 bpm=85.5
FILE mit_108_500.bin frames=36112 samples=902800 bad=0 peaks=2175 bpm=283.0
FILE mit_208_500.bin frames=36112 samples=902800 bad=0 peaks=2779 bpm=80.9
BATCH-END ok=3 fail=0 elapsed_ms=27895
```

- **`BATCH-END`** = 全部跑完（`ok=` 条数要对上 `total=`）。
- 实测速度：**3 条 27.9 s**，约 **9.3 s/条**（30 min 记录 ⇒ 约 195×）。
- 🛑 批处理期间**屏幕是黑的**，不是死机（日志明写 `screen idle until done`）。

### 2.3 回传结果

```bat
result-dump batch_mit_result.txt
```

或在 PC 侧一条命令落盘（推荐，避免串口工具截断）：

```bat
cd esp32\485tools
py esp_run.py --dump-only --stem batch_mit_result.txt --out _board_batch.txt
```

### 2.4 结果文件长什么样

```
BATCH-BEGIN total=3
# CardioLite S7 batch: fs=500 Hz, 每行最多 16 个峰索引
P 3 501 909 1316 1711 2105 2514 2841 3338 3760 4165 4561 4945 5366 5794 6204
P 6619 7030 7427 ... （16 峰/行，一直到该条结束）
FILE mit_100_500.bin frames=36112 samples=902800 bad=0 peaks=2272 bpm=85.5
P ... （下一条的峰）
FILE mit_108_500.bin ...
BATCH-END ok=3 fail=0 elapsed_ms=27895
```

**解析规则**：`P` 行按出现顺序累加 → 遇到 `FILE <name>` 就是当前这条的结束。
峰号是**文件内相对样本号**，可直接与 `_500.bin` / `_ann500.txt` 的坐标对齐。

## 3 路径 B：`mit-run`（有波形，可按倍速）

### 3.1 命令

```bat
mit-run 108 --speed 8       :: 结果写 /sdcard/mit_108_result.txt
mit-run 108                 :: 默认 1x，30 min 记录要跑 30 分钟
mit-run 108 5.00 --speed 4  :: 可选指定增益（只影响显示，不进检测器）
```

### 3.2 完成标志与**必看的 `dropped`**

```
FILE mit_108_500.bin frames=36112 samples=902800 peaks=2175 bpm=283.0
# dropped=0 speed=8 (逐位对账要求 dropped=0)
# 完整峰序列已写入 /sdcard/mit_108_result.txt（15354 B）
```

> 🛑 **`dropped=0` 是这份数据能不能用来对账的唯一开关。**
> 环缓满时 `push_sample()` 会**直接跳过检测器不喂样本**（设计行为），峰序列就与 PC 不一致了。
> 实测：1× 也丢过 **23%**（`fed=77700 / pushed=101075`），8× 反而是 0 ——
> **丢不丢取决于当时 UI 负载，与倍速不成单调关系**。

### 3.3 回传

结果文件名规则：`mit_108_500.bin` → 去 `.bin`、去 `_500` → **`mit_108_result.txt`**。

```bat
result-dump mit_108_result.txt
:: 或
py esp_run.py --dump-only --stem mit_108_result.txt --out _board_108.txt
```

### 3.4 什么时候不能用 `mit-run`

| 场景 | 原因 |
|---|---|
| 要证明"板端 = PC 逐峰一致" | 它可能丢样本，只差几个样本就足以让逐峰比对失败 |
| 只想快速出全 48 条 | 8× 也是每条 226 s，48 条 3 小时；**batch 只要 7.5 分钟** |
| FILE 源下想用 `rpeak rec` | 固件直接拒绝：`只在 485 实时源下记录` |

## 5 三道闸门：缺一条，结果就不能用

| # | 闸门 | 期望 | 不达标的含义 |
|---|---|---|---|
| 1 | `samples=` | **902800**（36,112 帧 × 25） | 帧解析/重同步出错，输入就不对 |
| 2 | `bad=` | **0** | 有坏帧，样本流不完整 |
| 3 | `dropped=`（仅 `mit-run`/`play`） | **0** | 环缓满、检测器跳过了样本 ⇒ 峰序列不可信 |

三条都过，才轮到"逐峰是否与 PC 一致"。

> 🛑 **不要用 σ、峰数、BPM 相近来判"一致"。** 判据只有一条：**峰索引序列逐个相同**。
> 理由：MIT-BIH 里本来就有 1 拍级的边界翻转（`fid` 开/关只差 3 拍），统计量完全掩盖不了。

**两套口径，报告里必须标清楚用的是哪一个**：

| 口径 | 回答什么问题 | 怎么出 |
|---|---|---|
| **完整数据（不剔边）** | 这批数据**全量、不做任何取舍**时算法表现如何 | `mitbih_compare.py --no-trim`（产物 `summary_full.csv`）；单文件用 `mitbih_eval.py` 的 `[全段]` 那组 |
| **剔首尾 5 s** | 与**文献 / 历史基线 W1 可比**时算法表现如何 | `mitbih_compare.py`（产物 `summary.csv`）；`mitbih_eval.py` 的 `[排除首尾 5s]` 那组 |

48 条实测（fid=1）：

| 口径 | 真值 | FP | FN | Se % | +P % | DER % |
|---|---|---|---|---|---|---|
| 完整数据 | 109,494 | 1,068 | 1,000 | 99.0867 | 99.0252 | 1.8887 |
| 剔首尾 5 s | 108,887 | 987 | 974 | 99.1055 | 99.0937 | 1.8009 |

> 🛑 **两者的差（−0.0188 / −0.0685 / +0.0878 pt）全部来自第 1 秒**，且那是**离线重放特有的伪条件**：
> 文件第 1 个样本就是信号，而检测器处于零初值。**真实设备上电时没有数据进入**（导联未接、AFE 未稳、
> 显示未就绪），不存在这种条件。所以它是"灌数据方式"的代价，**不是算法能力指标**。
> 逐秒证据：48 条合计第 1 秒 **56 FP / 22 FN**，第 2 秒降到 6 / 1，第 3 秒起为 0。

**取数示例（100 号）**：总峰 2272 → 窗内 2259（剪掉 13 个：窗头 6 + 窗尾 7），真值侧同步剪掉 14 拍。

## 9 MIT 验证覆盖不到的东西（必读，别拿 MIT 结果回答这类问题）

MIT-BIH 是**满负荷心电信号**：几乎每一秒都有真 QRS。因此它**永远触不到**"没有信号"这个分支。
以下几类问题**不能**用 MIT 的 Se/+P/DER 回答，必须单独验：

| 问题 | MIT 能回答吗 | 为什么不能 |
|---|---|---|
| 无输入时屏上会不会乱打点 | ❌ | MIT 里 `signal_peak` 被真 R 波拉到 ~10⁵ 量级，噪声过不了门；无输入时它才暴露 |
| 导联脱落 / 夹子悬空的表现 | ❌ | 同上；且需要 LOD 位才能判别 |
| 从空载切换到真实信号的起跳时间 | ❌ | MIT 没有"从无到有"的过程 |
| 算法在标准库上的检出能力 | ✅ | 这才是 MIT 的用途 |

### 9.1 「基线乱打点」的真正条件（2026-11-10 实测，已修正早期说法）

> **先纠一个我写错的结论**：早先写成"无输入就 4.6 拍/秒"，**条件没说清，是错的**。
> 现场反馈（AECG 关闭 / 未输出时**屏上零打点**）是对的，实测也支持。真正的条件是下面这条链。

**结论：乱打点需要的不是"有噪声"，而是「开机首个台阶很小」。**

同一段真机静息噪声（std 22.3 LSB ≈ 3 µV），**只在前面加不同的 DC 偏置**（等价于改变首样本
相对检测器零基线 `baseline=0` 的台阶大小）：

| DC 偏置 | 首样本 | 10 s 内峰数 | 结束时 `signal_peak` |
|---|---|---|---|
| 0 | 7 | **46** | 11.3 |
| 100 | 107 | **36** | 11.4 |
| **500** | 507 | **1** | 432.7 |
| 2000 | 2007 | **1** | 7,079 |
| 8000 | 8007 | **1** | 113,902 |

**机制**：首个检出峰的幅度决定了 `signal_peak` 的初值，而阈值是
`thr = noise + 0.25·(signal − noise)`。

- **台阶大**（如 MIT 文件首样本 ≈9000）⇒ `signal_peak` 被抬到 ~10⁵ ⇒ `thr` 高 ⇒ 噪声（积分 ~76）过不去 ⇒ **不乱报**；
- **台阶小**（首样本 ≈7~107，即录制起点贴着检测器零基线）⇒ `signal_peak` 只有 ~11 ⇒
  `thr ≈ 3` ⇒ **任何噪声起伏都过门** ⇒ 46 峰/10 s，且伪峰不断把 `signal_peak` 喂回去，**自我维持**。

**因此现场那三种"没输入"要分开看**：

| 条件 | 输入形态 | 结果 | 实测/依据 |
|---|---|---|---|
| AECG 关闭 / 未输出 | 近似**恒定**（无抖动） | **0 峰** | 合成恒定输入实测 0 峰（积分恒 0，严格 `>` 不成立） |
| 录制起点贴零 + 有本底噪声 | 台阶小 + 噪声 | **4.6 峰/秒** | 上表 DC=0/100 两行；对应真机录件静息段 |
| 导联夹悬空 / 脱落 | 开路拾取，幅度可能很大 | **未测** | 风险最高，必须单列（§9.3） |

> 🛑 所以：**"无输入还打点"不是必然，而是"起点台阶小 + 有噪声"这个组合**。
> 真机开机时 AFE 稳定后输出常接近 0 ⇒ 正落在这个组合里，所以现场能复现。
> 但换一台设备 / 换一次上电，直流工作点不同，就可能不复现 —— 这正是它危险的地方：
> **不是每次都有，但没有任何门控能保证没有。**

### 9.2 与「首秒伪影」的关系

同族但不同触发条件，别混：

| | 触发条件 | 表现 | 在 MIT 上的可见度 |
|---|---|---|---|
| **首秒伪影** | 首样本相对 `baseline=0` 的 DC 台阶 | 1 个伪峰（**48/48 条都在 sample 3**） | 可见（就是 T227 §2.3 那 56 FP 的主体） |
| **无输入自激** | 纯噪声、无真 QRS | **4.6 个/秒，持续** | **不可见**（MIT 里没有这种段） |

根因同一个：**检测器没有绝对幅度参照，只靠相对统计量。**

### 9.4 三状态实测汇总（2026-11-11）与测量纪律

**同一天、同一台设备、每次独立起流后测 12~30 s**：

| 状态 | 测量次数 | 打点密度（拍/秒） | 结论 |
|---|---|---|---|
| **AECG 上电但未输出** | 4（3.91 / 3.94 / 4.44 + 日志推算 3.73~4.50） | **≈3.7~4.5，稳定复现** | 最危险、可稳定复现 |
| **AECG 下电** | 5（0.11 / 4.15 / 0.00 / 1.08 / 0.09） | **0~4.15，随机** | 换次起流结果就变 |
| **导联夹悬空** | 3（0.06 / 0.00 / 0.00） | **≈0** | 推测输入饱和/钳位成恒定值 ⇒ 积分恒 0 |

**峰幅证据（AECG 上电未输出）**：打点处原始值 **min −172 / max 164 / 中位 −63 LSB（±26 µV）**，
邻域峰峰值中位 137；真实 R 波峰处 **≈9,923 LSB（≈1.5 mV）** ⇒ **幅度差 58 倍**，确认是噪声被当 R 峰。

> 🛑 **「AECG 开关决定有没有打点」这个直觉是错的**：下电那组 5 次里有一次到 4.15 拍/秒。
> 真正决定的是**每次起流时的直流工作点**（决定 `signal_peak` 初值 ⇒ 阈值），
> 与 `T227` §2.3.1 那张 DC 偏置表（46/36/1/1/1）同一机制。

#### 测量纪律（血泪换来的，测之前先看）

| # | 纪律 | 违反后果 |
|---|---|---|
| 1 | **测量期间不许 `rpeak reset`**（清屏本身已安全） | `rpeak reset` 会 `ecg_rpeak_reset()` ⇒ `peaks`/`fed` 归零、epoch 递增，`Δpeaks` 出现负数。⚠ **A-clear 之后清屏不再复位检测器**，可以放心按 |
| 2 | **判"零峰"只看 `Δpeaks` 计数，不能看 W 行** | 零峰时 `dump_buf_flush_to_file()` 在 `fill==0` 直接 return ⇒ `rpeak_hrv.txt` **不被覆盖**，读到的是上一次的旧峰 |
| 3 | **每次测完必须校验 `Δframes`** | `Δframes=0` 时 `Δpeaks=0` 只是"没数据"，不是"不打点"（今天踩了 3 次） |
| 4 | **`485-stat` 的「源：FILE」不可信** | `st.active = (s_src==RS485) && s_running` ⇒ **没在跑也显示 "FILE（SD 回放）"**；要判断真复位，看 `UART: ready/未初始化` |

> **`UART: 未初始化` 有两种成因，不要直接归因复位**（2026-11-11 订正，我先前判错过）：
> `s_ready` 只在 `rs485_init()` 置位、全工程无 deinit，所以它为 false 只能是——
> ①**芯片复位过**（上电初值 false）；②**`rs485_init()` 首次就失败**
> （`uart_param_config` / `uart_set_pin` / `uart_driver_install` 任一报错即 return，
> `s_ready` 永远停在 false，后续每次 `485-start` 同一错误重复失败）。
> **区分办法**：抓 `485-start` 的**完整回显** —— 打印 `485 源已启动…` = init 成功；
> 打印 `485 启动失败: <err>` = 走的是②。⛔ 只看命令回显那一行等于没取证。
