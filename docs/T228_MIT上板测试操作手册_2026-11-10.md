## 0 三十秒决定走哪条路

| 你想干什么 | 用哪条路 | 屏幕 | 速度 | 输入序列可信度 |
|---|---|---|---|---|
| **证明板端检测器与 PC 逐峰一致** | **`mit-set` + `mit-run-all`（batch）** | 黑屏 | 全速（30 min 记录 ≈ 9 s） | ✅ **权威**：逐样本同步喂，无环缓 |
| **看波形、看增益/走纸是否正常** | **`mit-run <rec> --speed N`** | 有波形 | 1/2/4/8× | ⚠ 走 pipeline + 环缓，**可能丢样本**，必须看 `dropped=0` |
| 只看波形、不要峰序列 | `play <file>` | 有波形 | 1/2/4/8× | 不写结果文件 |

**两条路各管一件事，别混用。** batch 看不到波形，`mit-run` 的峰序列不一定干净。

## 1 前置检查（三次命令，30 秒）

```bat
:: SD 上还有 48 条吗？（会递归列全卡 .bin）
scan

:: 板子在哪个模式、UI 是否正常
status

:: 485 源有没有被上次 play 抢走（batch 不需要 485，但排查时有用）
485-stat
```

**期望**：`scan` 能看到 `s7_batch/mit_100_500.bin … mit_234_500.bin` 共 48 个，每个 **2080 KB**。

**固件前提**：`ECG_RP_USE_STORED_FID = 1`（默认值）。若不是，板上结果会对应旧行为，不能与 PC 的 `fid=1` 比。

> （实测：软复位救不回来，见 §7.5）。

## 2 路径 A：`mit-set` + `mit-run-all`（batch，对账权威）

### 2.1 命令序列

```bat
mit-set 100,108,208          :: 写 /sdcard/batch_mit.txt；也支持 mit-set all（全 48 条）
mit-run-all                  :: 登记，提示"请重启"
restart                      :: 重启后**在 LVGL 之前**全速跑，屏幕黑屏属正常
```

`mit-set` 成功时会回读自检：`已写 /sdcard/batch_mit.txt：3 条 / 186 B（回读自检 3/3 ✓）`

### 2.2 怎么知道跑完了

串口会依次出现（**这是唯一权威的完成信号**）：

```
BATCH-BEGIN total=3
# CardioLite S7 batch: fs=500 Hz, 每行最多 16 个峰索引
FILE mit_100_500.bin frames=36112 samples=902800 bad=0 peaks=2272 bpm=85.5
FILE mit_108_500.bin frames=36112 samples=902800 bad=0 peaks=2175 bpm=283.0
FILE mit_208_500.bin frames=36112 samples=902800 bad=0 peaks=2779 bpm=80.9
BATCH-END ok=3 fail=0 elapsed_ms=27895
```

- **`BATCH-END`** = 全部跑完（`ok=` 条数要对上 `total=`）。
- 实测速度：**3 条 27.9 s**，约 **9.3 s/条**（30 min 记录 ⇒ 约 195×）。
- 🛑 批处理期间**屏幕是黑的**，不是死机（日志明写 `screen idle until done`）。

### 2.3 回传结果

```bat
result-dump batch_mit_result.txt
```

或在 PC 侧一条命令落盘（推荐，避免串口工具截断）：

```bat
cd esp32\485tools
py esp_run.py --dump-only --stem batch_mit_result.txt --out _board_batch.txt
```

### 2.4 结果文件长什么样

```
BATCH-BEGIN total=3
# CardioLite S7 batch: fs=500 Hz, 每行最多 16 个峰索引
P 3 501 909 1316 1711 2105 2514 2841 3338 3760 4165 4561 4945 5366 5794 6204
P 6619 7030 7427 ... （16 峰/行，一直到该条结束）
FILE mit_100_500.bin frames=36112 samples=902800 bad=0 peaks=2272 bpm=85.5
P ... （下一条的峰）
FILE mit_108_500.bin ...
BATCH-END ok=3 fail=0 elapsed_ms=27895
```

**解析规则**：`P` 行按出现顺序累加 → 遇到 `FILE <name>` 就是当前这条的结束。
峰号是**文件内相对样本号**，可直接与 `_500.bin` / `_ann500.txt` 的坐标对齐。

## 3 路径 B：`mit-run`（有波形，可按倍速）

### 3.1 命令

```bat
mit-run 108 --speed 8       :: 结果写 /sdcard/mit_108_result.txt
mit-run 108                 :: 默认 1x，30 min 记录要跑 30 分钟
mit-run 108 5.00 --speed 4  :: 可选指定增益（只影响显示，不进检测器）
```

### 3.2 完成标志与**必看的 `dropped`**

```
FILE mit_108_500.bin frames=36112 samples=902800 peaks=2175 bpm=283.0
# dropped=0 speed=8 (逐位对账要求 dropped=0)
# 完整峰序列已写入 /sdcard/mit_108_result.txt（15354 B）
```

> 🛑 **`dropped=0` 是这份数据能不能用来对账的唯一开关。**
> 环缓满时 `push_sample()` 会**直接跳过检测器不喂样本**（设计行为），峰序列就与 PC 不一致了。
> 实测：1× 也丢过 **23%**（`fed=77700 / pushed=101075`），8× 反而是 0 ——
> **丢不丢取决于当时 UI 负载，与倍速不成单调关系**。

### 3.3 回传

结果文件名规则：`mit_108_500.bin` → 去 `.bin`、去 `_500` → **`mit_108_result.txt`**。

```bat
result-dump mit_108_result.txt
:: 或
py esp_run.py --dump-only --stem mit_108_result.txt --out _board_108.txt
```

### 3.4 什么时候不能用 `mit-run`

| 场景 | 原因 |
|---|---|
| 要证明"板端 = PC 逐峰一致" | 它可能丢样本，只差几个样本就足以让逐峰比对失败 |
| 只想快速出全 48 条 | 8× 也是每条 226 s，48 条 3 小时；**batch 只要 7.5 分钟** |
| FILE 源下想用 `rpeak rec` | 固件直接拒绝：`只在 485 实时源下记录` |

## 4 脚本：从峰序列到 Se / +P / DER

### 4.1 `mitbih_eval.py` ★最常用（单条评分）

```bat
py mitbih_eval.py C:\work2026\CardioLite\mit_bih\records\108_ann500.txt _board_108.txt
```

**板端结果文件可以直接喂**（2026-11-10 扩了读取器：`P` / `W` / `index,time_s` / 纯索引四种格式都吃，
命令回显与 `cardiolite>` 提示符会自动跳过）。

实测输出：

```
[全段] 真值 1763  检出 2175  TP 1743  FP 432  FN 20
        Se 98.87 %   +P 80.14 %   DER 25.64 %

---- 排除首尾各 5 s（窗口 [2500, 900278] 样本 / 总长 902778 = 1805.6 s）----
[排除首尾 5s] 真值 1753  检出 2153  TP 1733  FP 420  FN 20
        Se 98.86 %   +P 80.49 %   DER 25.10 %
```

- **报告口径用「排除首尾 5 s」那一组**（原因见 §5）。
- 各指标定义见 `T227` §1.2。

### 4.2 `mitrun.py`（8× 批量抽样：自动跑 + 自动回传）

```bat
py mitrun.py --records 100,105,203,208 --speed 8 --outdir _board_mitrun8x
```

逐条执行 `mit-run` → 等 `FILE` 行 → 回传 `mit_<rec>_result.txt` → 落 `<rec>_8x.txt` + `<rec>_8x.log`。
结束时打印汇总表，并**单独列出 `dropped != 0` 的记录**。

实测（5 条 @8×，全部 `dropped=0`、每条正好 226 s）：

| 记录 | peaks | TP | FP | FN | Se % | +P % | F1 % | DER % |
|---|---|---|---|---|---|---|---|---|
| 100 | 2272 | 2259 | 0 | 0 | 100.00 | 100.00 | 100.00 | 0.00 |
| 105 | 2623 | 2550 | 58 | 8 | 99.69 | 97.78 | 98.72 | 2.58 |
| 108 | 2175 | 1733 | 420 | 20 | 98.86 | 80.49 | 88.74 | 25.10 |
| 203 | 2953 | 2876 | 58 | 90 | 96.97 | 98.02 | 97.49 | 4.99 |
| 208 | 2779 | 2756 | 8 | 183 | 93.77 | 99.71 | 96.65 | 6.50 |

> 这 5 条是**刻意挑的难例**，合计 97.59/95.72/6.77 **不代表全集**；全集 48 条是 **99.11/99.09/1.80**（T227 §2）。

### 4.3 `mitbih_compare.py`（PC 侧 48 条全量 + 逐峰对账）

```bat
py mitbih_compare.py                        :: 48 条 × {fid0, fid1}，约 30 s
py mitbih_compare.py --records 108          :: 单条
py mitbih_compare.py --skip-run --dump-count-events   :: 复用缓存，只重算统计 + 输出事件明细
```

- 缺 `_rp_cmp/rp_fid{0,1}.exe` 时**自动 gcc 构建**；
- 产 `_mitcmp/summary.csv`（96 行）、`_mitcmp/events.csv`（`rr==80` 逐例）、`_mitcmp/peaks/*.txt`（峰序列缓存）。
- ⚠ 它是**PC 侧**工具，不碰板子。

### 4.4 `rp_compare.py`（C 固件 vs Python 重放，逐峰）

```bat
py rp_compare.py        :: 编译 fid0/fid1 两个 exe，11 份 AECG 采集三方对账
```

用于"改固件后有没有改坏"：判据是 **①C(fid0)==Python(fid0) ②C(fid1)==Python(fid1) ③改动 100% 落在回溯峰**。

### 4.5 `esp_run.py`（485 实时记录 / 通用文件回传）

```bat
py esp_run.py --secs 180 --out _board_90bpm.txt   :: 485 实时：restart→485-start→START→rpeak rec 180→回传
py esp_run.py --dump-only --stem batch_mit_result.txt --out x.txt   :: 只回传任意 SD 结果文件
```

内置两道闸门：起记录前校验 `frames > 0`；结束后校验 `fed ≥ 0.97 × secs×500`。

### 4.6 工具速查

| 脚本 | 跑在哪 | 一句话 |
|---|---|---|
| `mitbih_eval.py` | PC | 单份峰序列 → Se/+P/DER（口径唯一来源） |
| `mitrun.py` | PC→板端 | `mit-run` 批量抽样，自动回传 |
| `mitbih_compare.py` | PC | 48 条全量 Se/+P/DER + 逐峰对账 + 事件明细 |
| `rp_compare.py` | PC | C 实现 vs Python 重放逐峰对比（改固件后必跑） |
| `esp_run.py` | PC→板端 | 485 实时记录；以及任意 SD 文件回传 |
| `pc485_cmd.py` | PC→STM32 | PC 直连 485 发下行命令（绕开 ESP32） |
| `pc_sweep_replay.py` | PC→STM32 | 多心率采集 + 离线算法对比一条龙 |

## 5 三道闸门：缺一条，结果就不能用

| # | 闸门 | 期望 | 不达标的含义 |
|---|---|---|---|
| 1 | `samples=` | **902800**（36,112 帧 × 25） | 帧解析/重同步出错，输入就不对 |
| 2 | `bad=` | **0** | 有坏帧，样本流不完整 |
| 3 | `dropped=`（仅 `mit-run`/`play`） | **0** | 环缓满、检测器跳过了样本 ⇒ 峰序列不可信 |

三条都过，才轮到"逐峰是否与 PC 一致"。

> 🛑 **不要用 σ、峰数、BPM 相近来判"一致"。** 判据只有一条：**峰索引序列逐个相同**。
> 理由：MIT-BIH 里本来就有 1 拍级的边界翻转（`fid` 开/关只差 3 拍），统计量完全掩盖不了。

**为什么报告用「排除首尾 5 s」那一组**：头部自适应阈值要几拍收敛（100 号第 3 个样本就是个伪峰），
尾部 EOF 处 60 样本积分窗填不满——这两段与检测能力无关。以 100 号为例：
总峰 2272 → 窗内 2259（**剪掉 13 个：窗头 6 + 窗尾 7**），真值侧同步剪掉 14 拍。

## 7 故障排查（全部为今日实发，按出现频率排序）

| # | 现象 | 真因 | 处置 |
|---|---|---|---|
| 7.1 | `rpeak rec` 报 **「只在 485 实时源下记录」** | FILE 源会覆盖 `mit-run` 的批处理结果，固件**主动拒绝** | 要板端峰序列就用 batch 或 `mit-run`，别用 `rpeak rec` |
| 7.2 | `485-start` 成功，几秒后 `485-stat` 又显示 `源: FILE`，`485-send` 报「485 未初始化」 | 之前 `play` 的文件生产者还在推样本，把源抢回去了 | **`restart`** 起干净状态；`esp_run.py` 默认先重启 |
| 7.3 | σ 算出 173、最大误差 4001 | 环缓满，检测器跳过了 23% 样本（`fed=77700 / pushed=101075`） | 看 `dropped` / `fed`；`rpeak off` 关打点降 LVGL 负载；重跑 |
| 7.4 | `result-dump` 回传 **0 字符** | `EspPort.wait_prompt()` 把累积字节读走后**丢弃**（只返回 bool） | 用 `esp_run.dump_file()`（自己攒到 prompt 为止） |
| 7.5 | **`scan`/`mit-set` 报「SD 卡未挂载」，软复位救不回来** | 批处理中途异常后 SD 状态机进坏态（**根因未定位**） | **断电重上电**。发生后重跑同类批次即可恢复正常 |
| 7.6 | batch 卡住：只有 `BATCH-BEGIN`，没有 `FILE` / `BATCH-END` | 同 7.5（首次即此现象） | 断电重上电后重跑；**排查时必先看 SD 是否挂载** |
| 7.7 | `mitbih_eval.py` 对板端文件报 `ValueError: invalid literal for int()` | 结果文件里有命令回显 / `cardiolite>` / `BATCH-*` 行 | 已在 2026-11-10 修：`P`/`W` 行识别 + 解析失败静默跳过 |
| 7.8 | 板端 `bpm=283.0` 看着像错 | 该记录（108）FP 多、中位 RR 短，PC 也是 283.02 | 不是分叉；属检测器在该记录上的**真实表现**（T227 §6.1 遗留风险） |

## 8 坐标系与文件命名（最容易搞错）

| 项 | 规则 |
|---|---|
| **峰号坐标** | **文件内相对样本号**（板端 `P` 行、PC `_det.txt`、`_ann500.txt` 三者同坐标，可直接比） |
| 采样率 | 500 Hz（`APP_SAMPLE_RATE_HZ`），与 `_500.bin` 一致 |
| batch 结果文件 | `/sdcard/batch_mit_result.txt`（由清单名派生：`batch_mit.txt` → `batch_mit_result.txt`） |
| `mit-run` 结果文件 | `mit_108_500.bin` → **`mit_108_result.txt`**（去 `.bin`、去 `_500`） |
| 结果格式 | `P` 行 16 峰/行；`FILE` 行是该条的分隔与汇总；`BATCH-END` 是全局收尾 |
| 标注在哪 | **SD 上只有 `.bin`，没有 `_ann500.txt`** ⇒ 评分必须在 PC 做 |
